# 潘多拉 Web 与管理端代码修改清单

> 记录日期：2026-10-25。
> 经需求核对，本文所列 14 项功能按 V3 PRD 的要求调整；另有五类现有行为已确认保留，其边界在下文说明。
> 本文记录待实施的代码修改要求，不表示代码已经修改或验收通过。

## 来源、范围与使用方式

- 需求对照：[V3 修订版 PRD](../requirements/潘多拉-产品需求文档-V3修订版.md)。
- 核对代码基线：`4a4b9b44df10692f5aa06597c44a40a5861acf72`。
- 下文“PRD 对应”中的章节号及验收项编号均指 V3 PRD，可据此定位需求原文。
- 范围：根目录员工 Web、`admin.html` PC 管理端，以及实现这些页面行为所需的后端接口；不包含安卓原生端。
- 核对证据以实际加载脚本、覆盖函数和相关后端源码为主，辅以内存执行确认日历入口与派发候选；未作完整浏览器、HTTP 或真机验收。
- 后续实施应先核对届时的代码与新需求，再处理仍存在的缺口；不能依据本清单覆盖后来已确认的变化。

已确认保留的行为包括：月/日两种日历模式和按天导航、可调整高度的月格及两行标题截断、日志部门/人员下拉筛选、受限上级只读查看撤回通知原内容、按角色初始化任务负责人。详见 [V4 编写前必读：已确认保留行为与修订参考](../requirements/潘多拉-产品需求文档-V4编写前必读-已确认保留行为与修订参考-新需求优先.md)。实施以下修改时须同时遵守这些边界。例如，恢复日历侧栏时仅保留月、日两种模式，不恢复周视图；调整日视图时间轴时保留可调整高度的月格。

## 待实施的代码修改项

### 日历及当日清单只展示本人负责的正常任务

- **PRD 对应**：2.2、5.2、A-13。
- **现状**：日历提供“查看日程”人员选择，可切换到管理链下属的负责任务。
- **应修改**：移除下属日程切换，月历、日历、全天区、跨日任务及当日清单统一使用本人当前有效负责人身份过滤正常任务。本人只是创建者或组织授权查看者的任务留在任务表单等授权入口。
- **验证结果应满足**：管理层也只能在日历看到本人负责的任务；负责人变化后按有效版刷新；待创建审核、未发布任务及历史通知只读例外不进入日历。不因此收回任务表单、详情、统计或下属资料的合法权限。
- **代码入口**：[日程视图](../../潘多拉-日程视图.js) 的 `calendarPeople`、`calendarPersonId`、`viewTasks`、`dayTasks`。

### 日视图恢复纵向完整时间轴

- **PRD 对应**：5.2.4、A-15、A-16；仅落实日视图相关要求，日历模式仍为已确认保留的月、日两种。
- **现状**：一天拆成三个八小时段，每段横向表示时间。
- **应修改**：日视图提供从 00:00 至 24:00 的纵向时间轴，可纵向滚动；全天任务在独立全天区，非全天跨日任务逐日按实际覆盖时段展示。可保留现有任务清单辅助模式。
- **验证结果应满足**：午夜边界、跨日和零时长任务可识别，置顶和点击尺寸不改写真正时段；保留月、日两种模式及按天导航，不新增周视图或整周滑动要求。
- **代码入口**：[日程视图](../../潘多拉-日程视图.js) 的 `segmentsFor`、`bandsHTML`、`layoutTimeline`、`dayHTML`，以及 [日历样式](../../潘多拉-日历.css)。

### 密集任务全量显示，取消日时间轴和全天区的聚合隐藏

- **PRD 对应**：5.2.3—5.2.5、A-15；仅实施仍保留的日视图相关要求。
- **现状**：时间轴最多直接展示五层，更多任务用“+N”展开；全天区也只直接展示前五项。
- **应修改**：日时间轴的重叠任务在当天宽度内横向分栏，全部可见、可点；全天区不再以五项上限隐藏其余任务，可通过滚动访问全量。
- **验证结果应满足**：超过五项的重叠任务和全天任务均能直接浏览、点击，不由聚合按钮代替；短任务的点击区域不遮挡其他任务。月格的容量上限及“+N”访问完整清单仍可保留，不把本项误应用到月格。
- **代码入口**：[日程视图](../../潘多拉-日程视图.js) 的 `VISIBLE_LANES`、`layoutTimeline`、`allDayHTML`。

### 恢复日历侧边展开面板与悬浮创建入口

- **PRD 对应**：5.2.1、A-13；模式数量仍为已确认保留的月、日两种。
- **现状**：模式、创建任务、我的申请集中在顶部，没有侧边展开面板和悬浮加号。
- **应修改**：顶部左侧提供展开按钮，面板承载月/日切换和本人申请入口；年月可打开日期选择器；右下悬浮加号打开原创建任务表单。侧栏收起后以日历为主体。
- **验证结果应满足**：悬浮入口不遮挡导航和关键内容，日模式可回今天；日历不增加任务名称搜索和任务统计区。任务表单入口同时按下文“接通任务表单的正常进入与返回路径”的要求接通。
- **代码入口**：[日程视图](../../潘多拉-日程视图.js) 的 `toolbar`、`runAction`，相关日历样式。

### 接通任务表单的正常进入与返回路径

- **PRD 对应**：5.2.1、5.2.7、A-26、A-27。
- **现状**：`潘多拉-任务表单.js` 已加载，具备表格、组合筛选、排序、计数、分页和打开详情的代码，但日历没有 `task-table-open` 按钮。
- **应修改**：在日历顶部加入明确的“任务表单”入口，复用已有二级页面；检查返回日历时模式和日期保持，以及授权变化后的刷新路径。
- **验证结果应满足**：普通用户通过页面按钮即可进入；本人同时创建和负责的任务分别计入两类关系但行不重复；筛选、排序、计数作用于完整授权结果集，再分页；待创建审核和历史通知例外隔离。不能继续引用旧报告将整个表单误判为尚未实现，也不能仅补按钮就宣称其余功能已通过验收。
- **代码入口**：[日程视图](../../潘多拉-日程视图.js) 的 `toolbar`；[任务表单](../../潘多拉-任务表单.js) 的 `openTable`、`closeTable`、`computeTaskForm`。

### 派发候选与后台配置的独立派发权限一致

- **PRD 对应**：2.1、2.2、A-02、A-03。
- **现状**：Web 使用 `/users` 的人员数据，再按旧角色和同团队规则过滤；人员映射还将团队名称当作部门标签，可能漏掉同部门不同团队的授权人员。
- **应修改**：使用后端授权的派发候选接口，移除角色、同团队等旧规则对候选及提交的二次错误限制；部门展示使用真实部门字段。候选页面和保存前检查采用同一权限口径，适配组织及授权变化。
- **验证结果应满足**：本部门有权派发但不同团队的下属可选；配置为本人、直属下属、部门或公司范围后，候选与后端裁决一致。任务可见、人员资料可见或团队负责人身份不自动授予派发权限。
- **代码入口**：[任务接入](../../潘多拉-任务接入.js) 的 `assignablePeople`、`saveTask`；[API 接入](../../潘多拉-api.js) 的 `mapPerson`；[基础负责人选择器](../../潘多拉-交互原型.js)；[候选接口](../../backend/src/main/java/cn/pandora/task/TaskController.java) 的 `/assignee-candidates`。

### 普通任务表单展示真实审核人及正确路由

- **PRD 对应**：4.3、A-06、A-07。
- **现状**：普通创建仅提示由系统确定审核人；编辑展示旧审核人，并写明沿用当前负责人路线。后端实际按提议负责人路由，专用交接已有预览。
- **应修改**：创建、编辑及重新提交表单随有序负责人变化请求审核预览；展示实际审核人，无审核人时显示原因。负责人变更按新负责人计算，普通详情和申请详情正确区分当前有效审核人与本次申请审核人，去除旧路线误导。
- **验证结果应满足**：同级负责人换序、跨管理链、负责人变更及无可用审核人场景的预览、提交和详情一致；旧预览不能覆盖新选择；提交仍由后端重新计算。
- **代码入口**：[任务接入](../../潘多拉-任务接入.js) 的 `taskFormView`、`requestHandoverPreview`；[审核预览接口](../../backend/src/main/java/cn/pandora/task/TaskController.java) 的 `/tasks/reviewer-preview`。

### 修正“创建者等于审核人自动免审”的旧提示

- **PRD 对应**：4.3、A-07。
- **现状**：进展、完成、重开表单仍提示本人等于审核人时免审，但后端实际上会产生待审申请。
- **应修改**：统一提示为存在审核人就须明确审核，即使申请人与审核人为同一人；确实无审核人时才按记录的原因直接生效。排查相关表单和结果文案，避免继续表达旧规则。
- **验证结果应满足**：自审操作提交后仍为待审，须在审核入口决定；不为迁就旧提示改动后端的正确规则。
- **代码入口**：[任务接入](../../潘多拉-任务接入.js) 的 `actionView`；[后端提交规则](../../backend/src/main/java/cn/pandora/task/TaskService.java) 的 `submit`。

### 重开申请可一并调整排期

- **PRD 对应**：4.2、4.5、5.6.2、A-10。
- **现状**：Web 重开只提交原因，无排期编辑；原截止时间已过时，后端拒绝提交，用户无法通过现有页面完成重开。
- **应修改**：重开表单支持全天标记、起止日期和非全天时刻，将有效排期与原因一起提交，复用后端已有重开排期能力。
- **验证结果应满足**：已过旧截止时间的已完成任务，可提交未来排期并经审核重开为进行中；拒绝、撤销或失效仍保持原已完成状态，排期和提醒去重按新轮次规则处理。
- **代码入口**：[任务接入](../../潘多拉-任务接入.js) 的 `actionView`、`saveAction`；[后端任务服务](../../backend/src/main/java/cn/pandora/task/TaskService.java) 的 `reopen` 分支。

### 创建申请失效后可调整并重提

- **PRD 对应**：4.4、5.6.2、A-21。
- **现状**：Web 重提按钮和校验只接受 `rejected`、`withdrawn`，遗漏 `expired`。
- **应修改**：为创建申请失效结果提供清晰状态及“修改并重提”入口；仅原申请人可操作，载入原提议后调整排期，创建新的申请，不能恢复旧申请为待审或继续批准旧申请。
- **验证结果应满足**：失效创建任务仍不进入正常任务区；本人可改期重提；旧审核按钮、重复提交和并发决定不能让旧申请再次生效。
- **代码入口**：[任务接入](../../潘多拉-任务接入.js) 的 `resultName`、`approvalDetailView`、`resubmitCreate`。

### 审核界面使用逐项差异，识别负责人换序

- **PRD 对应**：4.1、4.3、4.4、A-06、A-10。
- **现状**：后端提供逐项 `diff`，Web 自行概括变化字段；比较负责人时先排序，导致仅换序的变更不被标明。
- **应修改**：审核界面展示字段前后值，使用后端授权返回的差异数据；负责人按保存顺序比较与呈现，明确换序影响，不再按集合等同处理。
- **验证结果应满足**：同一组负责人仅换序也显示前后顺序差异及对应审核人；专用差异对比只向本次审核人展示，申请人仍仅按自身权限跟踪提交内容，不因前端接入 diff 扩权。
- **代码入口**：[任务接入](../../潘多拉-任务接入.js) 的 `differenceHTML`、`approvalDetailView`；[后端差异 DTO](../../backend/src/main/java/cn/pandora/task/TaskService.java) 的 `requestView`、`diff`。

### 正式 PC 管理端提供完整任务历史查询

- **PRD 对应**：3.3、4.6、A-11、A-28。
- **现状**：后端有 `/admin/tasks/{id}/history`，正式管理页面没有查询栏目；调试页的简略审计列表不能替代。
- **应修改**：在正式管理端提供任务查找或定位和完整历史展示，接入已有接口；展示时间、操作人、字段前后值、有序负责人、申请与决定、意见、改派、失效、交接、重开及免审原因等可追溯信息。任务查找所缺的接口按管理员权限补齐。
- **验证结果应满足**：管理员可在 PC 页面独立完成查询；员工直连接口仍被拒绝；个人删消息、撤回和消息到期不删除任务历史；员工 Web 不新增完整历史入口。
- **代码入口**：[正式管理端](../../admin.html) 的 `state.tabs`；[管理端历史接口](../../backend/src/main/java/cn/pandora/admin/AdminController.java)；[任务历史服务](../../backend/src/main/java/cn/pandora/task/TaskService.java)。

### 正式 PC 管理端提供通知管理

- **PRD 对应**：3.3、5.6.3、A-22、A-28。
- **现状**：后端有管理员通知列表与事件撤回接口，正式页面没有入口。
- **应修改**：新增正式通知管理栏目，接入列表和权限内撤回，呈现接收、已读、撤回及保留期等可用状态；撤回结果明确不撤销任务或申请，也不删除审计。
- **验证结果应满足**：管理员可在 PC 页面管理通知；撤回严格遵守发送后三分钟时限；普通业务账号不能直连越权。已确认的“受限上级只读查看撤回通知原内容”行为须保留，不能借通知管理功能恢复任务跳转或审核按钮。
- **代码入口**：[正式管理端](../../admin.html)；[通知管理接口](../../backend/src/main/java/cn/pandora/workspace/WorkspaceController.java)；[通知生命周期服务](../../backend/src/main/java/cn/pandora/workspace/WorkspaceService.java)。

### 获授权部门负责人可通过页面创建团队和转交负责人

- **PRD 对应**：2.1、2.2、A-02。
- **现状**：后端支持团队管理能力，但员工 Web 没有入口；现有管理页面首先读取管理员专用组织数据，部门负责人无法通过该页面完成操作。
- **应修改**：为获授权部门负责人提供受限团队管理入口与必要读取能力，复用后端创建、转交逻辑，不以登录完整管理控制台为前提。入口位置可在后续界面设计中确定。
- **验证结果应满足**：获授权者可在权限内创建团队，创建者默认负责并可按权限转交；无授权者不可操作；团队负责人身份不自动扩大任务派发或查看权；员工 Web 不因此嵌入完整管理员维护模块。
- **代码入口**：[团队服务](../../backend/src/main/java/cn/pandora/admin/OrganizationService.java) 的 `createTeam`、`updateTeam`；[管理端组织读取](../../backend/src/main/java/cn/pandora/admin/OrganizationService.java) 的 `structure`；员工 Web 中适当的团队操作入口。

- 保留已确认行为：月/日两种模式和按天导航、可调整月格及两行标题、日志部门/人员下拉筛选、受限上级查看撤回通知原内容、按角色初始化负责人。
- 既有正确行为应回归：日志全屏编辑与每日冻结、通知列表无底部刷新/关闭栏、管理链手机号隐私、管理员建号和强制改密、独立 PC 管理端与后台鉴权、有效版隔离及任务唯一待审。
