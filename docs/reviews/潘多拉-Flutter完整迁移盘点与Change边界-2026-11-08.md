## 1. 已确认的目标与判断口径

目标是用 Flutter 构建完整员工安卓客户端，复用现有后端，以现有员工 Web 的实际有效行为为主要参考，再叠加 11 月 8 日更改指导。不是只实现新指导中的 12 项，也不是只做五个页面的空壳。

已确认的边界：

1. 员工 Web 用于参考和过渡，不要求作为长期对等客户端持续完整同步新交互。
2. 独立管理员继续使用 PC Web，不迁移整个管理端到 Flutter。创始人、部门负责人、团队负责人、普通员工都是员工客户端角色，其业务能力必须迁移。
3. 早期 `android/` Java 原生工程未验证，基本不作为迁移基线；`android-shell/` 用于理解过渡安装与运行环境，不是 Flutter 功能完成证明。
4. 系统推送继续延期。首轮保留完整站内通知；后台或应用未运行时的安卓系统通知不在首轮交付范围。
5. 本轮只完成调查，不提前提出 change 或实施。

建议保留两个候选 change：A 处理共享后端、数据契约和必要 PC 管理端/过渡适配，B 交付完整 Flutter 员工端。**先完成 B 的完整业务盘点和关键交互契约设计，再实施 A；A 的范围是为完整迁移补缺，不只是落实 12 项后端修改。** 已满足的服务继续复用。

事实与需求分开判断：新指导中明确修改的业务规则优先；未被修改的主规格规则继续有效。代码用于确认当前能力和差距，不能把代码偏差自动提升为需求。旧 PRD、工程说明、归档记录用于追溯，不能覆盖较新的明确规则。新指导原先的“套壳/Web 交付”载体约束，需在未来 change 中依照本次 Flutter 决定调整；其余确认的业务规则承接。

### 6.2 跨端容易误接的既有约束

1. **登录字段和强制改密不同响应名。** 员工请求为 `{accountType:"employee",phone,password}`，服务严格检查字段；管理员用 accountName，不用 username。登录返回 token/tokenType/expiresAt/user/passwordChangeRequired；会话查询为 mustChangePassword。受限态只允许会话查询、改密、退出，不能先拉 `/me` 或刷新绕过。密码至少 10 位、含字母数字、UTF-8 最多 72 字节，需旧密码；改后所有会话失效。
2. **版本与重试。** 对象修改按端点使用 `If-Match: "rowVersion"`，幂等键为 8–80 位 `[A-Za-z0-9._:-]`。同一操作/请求体/版本因网络不确定而重试沿用同一键；改内容/新操作换键。428 缺版本、412 旧版本、409 业务/资格冲突，失权对象常以 404 隐藏。不能自动无条件覆盖、反复生成新键重放，也不能把旧授权下缓存的成功结果当永久通行证。
3. **分页并不统一。** 任务 `nextCursor` 当前实为数字偏移字符串；日志/通知/事项使用 nextOffset；评论 nextCursor 是评论 ID 游标；申请有 limit/offset。Flutter 应分别解析，避免统一把 cursor 转 int。范围加载只有读完全部页/明确完备标志才能宣称完整；取消过期查询、防重、账号/人员/条件隔离同样属于实现范围。
4. **个人表单不是直接展示 `/tasks`。** `TaskService.filteredTasks` 输出正常授权结果；Web 在 `任务表单.js` 中先拉全量页，再做“原始创建或当前负责”的关系并集、组合筛选、排序和分页。A 必须在“后端提供个人表单完整查询管线”和“完整拉取后客户端管线”之间定案，并验证超过一页的计数/置顶/稳定性。推荐将全局管线放后端，但这是建议，尚未确认接口方案。
5. **权利按操作和上下文区分。** `editableFields/canReschedule/canPin/canHandover/handoverSources` 是 UI 依据，服务端每次重验。正常详情、下属只读浏览、历史通知只读必须有明确路由上下文，不能复用一个“可见即能操作”的详情组件。隐藏组织身份文本不删除角色与管理链数据。
6. **日期不可混用。** `/me.organizationTimeZone` 与 `/home.businessDate` 是现有依据。date-only 不转 UTC 午夜再取本地日期；日志 businessDate 与 createdAt、事项结束日与小时截止、旧 allDay 与定时整日覆盖分别处理。日历覆盖/日志填充中午夜截止不占次日，零时长不伪造成整天；个人表单的日期筛选则按主规格的起止所属公司日期相交规则，不擅自与绘制规则混同。旧全天提醒截止默认 18:00，PC 下班时刻修改只影响之后新排期/修订，旧有效/在审排期保留快照；不能从显示全天区反推提醒。零工期无比例提醒，逾期和完成仍按原服务规则。
7. **有效版、提议、历史分离。** 待审任务 DTO 的 pendingSchedule 仅给日历投影用；普通资料、表单、提醒仍有效版。申请人/审核人/普通读者字段投影不同。原创建者、当前业务责任方、当前负责人、申请人、审核人是不同关系，正式接管不修改 provenance 或“我创建”。
8. **集合不得降级。** 任务和日志使用稳定顺序的 tagIds/tags；旧首项投影不能作为全部标签。负责人顺序变化是实际变更。删除标签快照可保留并移除，不允许移除后重新新挂回删除项。
9. **照片不是原图上传接口。** Web 当前允许源 PNG/JPG 至多 10MB，再中心裁剪为 256px JPEG；服务校验压缩后图片二进制最多 300,000 字节、尺寸不超过 512px、完整 data URI 字符串最多 400,000 字符。B 应做等效选图/裁剪/压缩及错误反馈，压缩后再次校验；不能把源图限制误作服务端承诺。
10. **不要恢复退休接口。** 员工旧 `/home/items*` 的个人写入已返回 `410 HOME_ITEMS_PERSONAL_RETIRED`，公司维护属于 PC。管理测试时钟/worker 调试入口、早期 Java 端假接口和基础脚本未生效功能不进入产品范围。

## 8. 两个候选 change 的边界、顺序与共同约束

以下是候选边界，不是已经创建的 change 名称或最终 tasks。建议 A 可命名为“员工端迁移所需共享契约与业务升级”，B 可命名为“完整 Flutter 员工安卓端”。两者共同引用本文清单与 J 场景，不能让 B 的范围退化为只做 12 项交互。

### 8.1 A：共享业务、契约与必要管理端升级

纳入：D02/D05 数据及范围读取、F04 独立偏好和 F02/F03 全局管线定案、Q05 节假日服务、P03 真实入职字段及 O01 PC 维护、P04 授权下属邮箱、L06 名称读取契约、Q02 迁移、Q03 动画演示、Q06 过渡兼容。补充 B 完整迁移所需而现有服务确实欠缺的字段/能力提示，并维护相关接口文档与关键契约回归。

复用且针对相关风险回归：登录/强制改密、角色授权、任务字段编辑/负责人/审批/交接/到期、日志唯一与冻结、多标签/评论、通知生命周期、统计/建议、PC 原子组织管理和审计。没有发现必须重写这些完整服务的证据；也不能仅因不用重写就从 B 迁移清单删掉。

不把 Flutter 页面、手势、日历布局、手机照片和 APK 作为 A 的已完成事项。A 的完成条件是：必要服务/管理端/迁移/演示/过渡可独立验证；关键契约明确且有适合的数据及负向场景证明。A 的验证必须覆盖 B 会用的真实响应、全局分页、资格失效和时间边界，不能仅靠单字段 CRUD 成功。

### 8.2 B：完整 Flutter 员工安卓交付

第 3 节全部员工端清单均属于 B 的需求范围，包括“复用→B”的原有业务；使用 A 最终契约及未改变的服务。完成所有页面/二级入口、四类员工角色、完整任务/审核/交接流程、个人表单、各类日历、日志/标签/评论、下属工作区、通知、统计建议、个人资料及安卓交付。

B 可以按基础设施→纵向业务流程→复杂日历→完整回归分阶段开发，但阶段性页面不等于完整 change 完成。安卓构建、安装及四角色真机/设备业务验收必须有证据，后端检查或 Web 截图不能代替。PC 管理原功能继续运行，由 A/B 联调回归确认。

### 8.3 减少两个 change 后续互修的方法

推荐顺序：

1. 用本次完整清单确认范围，先把关键 B 交互转化为 A 可验证的数据与操作契约，尤其跨日事项、全局表单、下属上下文和日期边界。
2. 提出并完成 A 的 proposal/design/specs/tasks；这些文档从完整迁移倒推，不能只引用 12 条指导。设计里落定第 6.3 节问题，准备代表性的请求/响应与多页数据。
3. A 实施、独立验证、归档，使主规格与真实契约一致；B 在 A 的最终规格/接口基线上正式提出。A 设计阶段可预先审视 B 的业务分组与交互草图，不要求提前创建 B 或开始写 Flutter。
4. B 对照原清单逐项实现及验证。确实发现共享需求遗漏时显式修正规划与责任归属；不能客户端伪造、放宽权限或并行维护两套相反的 delta specs。

这样 A 有独立可交付结果，B 有全量范围及稳定依赖。两个 change 仍会正常联调，但不靠“后端先把 12 项做完，再看 Flutter 缺什么”来定义契约。

### 8.4 过渡 Web 的兼容责任

用户已确认它是参考和过渡，未确认“现在立即停止使用”。A 设计必须确定切换窗口：可以保留旧单日请求对新范围的安全映射、调整最小必要读取/编辑逻辑，或明确受控停用相关旧入口并安排切换。不得让旧客户端无声地把跨日事项缩回单日，或误改新偏好。

不要求 A 把每日事项连续月历、完整手机拖动、通知新布局等在 Web 全做一遍。但具体哪些旧入口仍承诺可用、如何安全承接数据、是否需要最小 UI/版本提示，要在设计中给出可验证结果；若方案需要真正停止员工 Web 或改变过渡服务承诺，再由用户确认该发布安排。
