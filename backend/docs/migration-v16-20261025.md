# V16—V19 迁移、预检与恢复说明（2026-10-25）

本文件说明本次变更新增的前向迁移、迁移前预检、隔离演练、重复启动的行为以及恢复步骤。所有命令都在
`backend/` 目录执行，且只在项目自带的 MySQL（127.0.0.1:13306）与隔离数据库中操作。

## 1. 迁移内容

| 版本 | 文件 | 内容 | 失败/回滚关注点 |
| --- | --- | --- | --- |
| V16 | `V16__work_log_day_slot.sql` | 日志改为逻辑删除：新增 `deleted_at`、`recovered_from`，保留原 `uq_log_day(organization_id,author_id,business_date)` 日位置唯一键 | 只加列与索引；无重写。历史被物理删除的日志由启动回填 `WorkLogSlots` 依据可证明的 `log.created`/`log.deleted` 事件还原为“正文为空、已删除、保留原首次创建时间”的行 |
| V17 | `V17__tags_and_task_tag_snapshot.sql` | 公司级 `tags` 目录；`task_versions.tag_id`（单值）与名称/颜色审计快照；`work_logs.tag_id`（单值）；复合公司外键与索引 | 既有任务/日志一律保持“无标签”，不回填标签值；多标签在存储层不可表示 |
| V18 | `V18__flat_comments.sql` | 任务/日志平铺评论 `task_log_comments`：对象类型+单一对象引用、作者、编辑/删除状态、行版本、按对象和稳定时间/ID 的分页索引 | 只新增表；`work_logs` 增加 `(organization_id,id)` 唯一键以承载公司隔离外键 |
| V19 | `V19__employee_phone_login.sql` | 员工独立登录键 `users.login_phone`：由既有联系电话规范化回填；缺号/重复号登记为阻断项；无冲突时才启用唯一索引；管理员保持用户名登录且不获得员工登录键 | 不生成号码、不新建账号；有重复或缺失时唯一索引不启用并保留阻断记录 |

V1—V15 一个字节都没有改写。Flyway 在启动时会校验已应用迁移的 checksum；隔离演练能直接启动到 V19，说明旧迁移校验通过。

## 2. 迁移前预检

```sh
python3 scripts/migration_precheck.py --database <库名> precheck --output ../audit/precheck.json
```

预检只读（`SELECT/SHOW/DESCRIBE`），报告包括：

- 部门/职位映射缺口；
- 同人同日重复日志；
- 负责人顺序与派发时间是否有可证明来源；
- 通知与申请的绑定缺口；
- **员工登录键**：缺号、规范化后无效、规范化后重复（只输出对象 ID 与脱敏号码）；
- **员工组织树**：根节点数量、悬空上级引用、循环；唯一根才会被认定为创始人；
- **历史完成标准统计**：版本数、有值/空值数、当前有效任务中有值的数量。

阻断项需要管理员通过既有维护流程修复；预检不会自动改数据。

## 3. 隔离演练（推荐在每次数据修复前后各跑一次）

```sh
python3 scripts/check_migration_foundation.py --output ../audit/2026-10-25/chapter1-migration.json
```

脚本会：

1. 把 `database/pandora.sql` 恢复进 `pandora_precheck_foundation_*` 一次性数据库；
2. 记录迁移前的员工 ID、任务/版本/负责人/申请行数、每条日志的真实 `created_at`；
3. 模拟一次旧代码的物理删除（仅保留可证明的 `log.created`/`log.deleted` 审计与事件）；
4. 启动本机构建，让 Flyway 前向执行 V16—V19，并等待启动回填写入结果；
5. 核对身份与关联未变、存活日志的 `created_at` 未重置、被删除的日位置已还原、标签/评论/登录键结构与公司隔离约束成立；
6. 通过管理员接口创建真实部门/职位、指派并录入手机号，证明“缺号 → 管理员修复 → 登录键可用”的修复路径；
7. 再次启动，证明重复启动不会重复迁移或重复回填；
8. 删除一次性数据库（`--keep` 可保留）。

演练默认不接触 `pandora` 业务库；报告写入 `audit/`，其中不包含明文号码或任何凭据。

## 4. 修复与上线顺序

1. 备份当前库，并在隔离副本上跑第 2、3 节的预检与演练。
2. 先处理阻断项：为在职员工补齐真实手机号；解决规范化重复号；修复组织树多根/悬空/循环与部门职位映射。**不要**用脚本生成号码或重建账号来“消掉”阻断项。
3. 部署后端（V16—V19 自动执行）。确认 `migration_findings` 中 V16—V19 的记录符合预期（被物理删除且可证明的日志已还原；无法证明的记为 limitation）。
4. 部署同一版本的员工 Web/管理端静态资源；员工改用手机号登录，管理员保持原用户名登录。
5. 用隔离演练和 `scripts/run_check_isolated.sh` 下的检查脚本验证；实际业务库的验收以独立 e13 验证为准。

## 5. 恢复步骤

- 迁移是前向的：优先“前向修复”（补数据、补映射、修复组织关系），不要回写历史迁移文件。
- 需要回到迁移前状态时，必须**服务、Web 资源与数据一起回退**，仅回滚二进制会重新引入物理删除、旧审核路线等问题，并可能与新增列/引用冲突。
- 数据恢复只在隔离库演练：

```sh
cd backend
./scripts/start-db.sh
mysql --defaults-file="$PWD/.runtime/mysql-admin.cnf" -e 'CREATE DATABASE pandora_restore CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;'
for h in localhost 127.0.0.1; do
  mysql --defaults-file="$PWD/.runtime/mysql-admin.cnf" -e "GRANT SELECT,INSERT,UPDATE,DELETE,CREATE,ALTER,INDEX,REFERENCES,DROP ON \`pandora_restore\`.* TO '$PANDORA_DB_USER'@'$h';"
done
mysql --defaults-file="$PWD/.runtime/mysql-admin.cnf" pandora_restore < <迁移前备份>.sql
python3 scripts/migration_precheck.py --database pandora_restore precheck
```

- 恢复库验证通过后再切换连接；恢复演练不得直接覆盖正在使用的业务库。
- V16 还原的“空正文、已删除”行是日位置占位，不应当作业务内容导出或回填正文。

## 6. 已验证结果

`audit/2026-10-25/chapter1-migration.json` 记录了本机一次完整演练的逐项结果（17/17）：旧数据身份与关联未变、
日志 `created_at` 未重置、可证明的历史删除还原成功、既有日志合并均有归档、标签/评论/登录键约束成立、
管理员修复路径可用、重复启动不重复回填。该证据只说明本机隔离演练，不替代独立 e13 验证或真实生产数据演练。
