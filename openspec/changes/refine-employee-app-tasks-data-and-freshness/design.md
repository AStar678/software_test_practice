## Context

当前 Flutter 任务表单通过 `TagSelector` 只读取创始人维护好的标签目录；标签 `POST /tags` 已存在且仅创始人可用，缺的是表单内联入口。任务表没有删除字段，`notifications`、`approval_requests`、`task_records`、`work_logs`、`domain_events`、`reminder_receipts` 等均以任务为外键，硬删除会破坏历史。每日事项当前只有 `start_date/end_date`，逾期按公司 `businessDate > endDate` 判断。首页事件纪与任务看板没有序号，负责人候选按姓名返回，Flutter 名称渐隐把末字同时留在前缀和遮罩层中，因此出现重影。底部导航只在切换分支时调用 `goBranch`，不主动刷新目标页数据；通知和我的下属已有下拉刷新，但部分相关浏览层没有统一刷新语义。

周视图双指手势本次明确不做，继续保留现有标题入口和双指调周高。管理端员工生命周期与文案清理在独立 admin change 中处理。动机见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- 在现有权限模型内补齐创始人任务表单内联标签创建，不扩大标签维护权。
- 用软删除保存任务及其全部历史引用，并让所有员工端入口一致识别已删除任务。
- 在不改变日历天级展示的前提下，给每日事项增加全天/定时两种模式及精确逾期判断。
- 用轻量刷新协调器让底部导航每次点击都拉取新数据，同时保留页面本地浏览状态。
- 在不改变服务端排序和首页上限的前提下增加纯展示序号。
- 让负责人候选和名称渐隐在 Flutter 与既有 Web 行为上保持一致。
- 建立员工 App 的用户可见错误安全边界。

**Non-Goals:**

- 不实现周视图双指进入/退出，不改变现有双指调周高。
- 不放宽标签维护权给普通员工，不新增私人标签。
- 不物理删除任务，不级联删除通知、申请、评论、日志或历史。
- 不改变每日事项的日历精度、条带绘制、私有归属和日志无关性。
- 不新增员工 Web 删除入口；只保证共享接口对已删除任务返回可识别状态。
- 不实现管理端员工入职/离职/筛选/身份证号/管理端文案清理，这些属于独立 change。

## Decisions

1. **标签内联创建复用现有接口和表单状态。**
   - 在 `TaskFormPage` 的标签区，仅当 `currentUser.isFounder` 且 `_can('tagIds')` 时显示“新建标签”。
   - 打开当前页内的弹窗，复用名称、40 字限制、八色预设和重复名校验；提交现有 `POST /tags`，成功后把返回标签加入 `_tagCatalog` 与 `_selectedTags`。
   - 不导航到 `TagManagePage`，因此标题、说明、排期、负责人、父任务等既有状态不需要序列化或跨会话恢复。
   - 失败只显示中文错误并保留全部表单状态；取消内联弹窗不改变选择。
   - 备选“跳转标签页再返回”需要额外草稿存储和返回协议，且会丢失滚动与焦点，不采用。

2. **任务删除采用带版本校验的软删除。**
   - 新迁移在 `tasks` 增加 `deleted_at`、`deleted_by` 和删除原因等最小字段；`row_version` 随删除递增。
   - 新 `DELETE /tasks/{id}` 要求 `If-Match`/当前版本与幂等键；权限为当前业务责任方或原创建者。存在 `pending` 申请时返回明确中文冲突，不修改任何记录。
   - 删除只更新任务行并写入任务操作历史/领域事件，不删除版本、申请、评论、日志、通知、交接、业务接管或提醒回执。
   - 任务列表、日历、看板、统计、父任务候选、任务表单和搜索均排除 `deleted_at IS NOT NULL`。任务详情对已删除返回 `TASK_DELETED`（HTTP 410 或同义稳定错误），只给客户端最小标题/删除提示。
   - 已存在的 `task_id` 引用保持不变；通知、申请、日志关联读取到已删除任务时，共享投影返回 deleted 标记，客户端显示“任务已删除”。父任务被删除时，子任务按既有 `parentUnavailable` 语义处理。
   - 管理端历史查询保持按任务 ID 可读，删除记录作为历史的一部分；管理端页面和行为留给 admin change。
   - 备选物理删除需要级联或置空大量外键，破坏申请、通知和历史，拒绝。

3. **任务删除入口避开拖动冲突。**
   - 月视图不在任务条上增加新的长按动作；本人当天清单、任务详情、任务表单和日志关联任务操作提供删除入口。
   - 删除前显示确认，说明申请/通知/日志不会删除；成功后关闭当前表单/详情并刷新来源页。失败保留原页面和表单状态。
   - 下属浏览、历史只读和仅可见访问不显示删除入口，后端仍做最终校验。

4. **每日事项采用“日期范围 + 全天标记 + 可选起止时刻”模型。**
   - 保留 `start_date/end_date`，新增 `all_day`、`start_time`、`end_time` 可空字段；旧记录迁移为 `all_day=true`、时刻为空，日期、ID、正文、完成、版本和时间不变。
   - 定时事项要求两个时刻；日期与时刻按公司时区解释。跨日定时事项仍是一条记录，覆盖日由日期范围计算。
   - 服务端状态：完成后为 `completed`；全天项按 `businessDate > endDate`；定时项按公司当前时刻严格晚于截止日期+截止时刻。恰好等于截止时刻仍为 `open`。
   - API 增加 `allDay`、`startTime`、`endTime`；旧客户端只提交日期时默认按全天保存，响应仍保留原 `startDate/endDate`。Flutter 表单增加全天/定时切换和时刻输入，日历/摘要保持天级投影。
   - 备选改为全 datetime 模型会重写范围查询和既有日期索引，兼容成本更高，不采用。

5. **刷新采用页面级刷新信号，不重建导航分支。**
   - 在 App 层增加可监听的“tab 刷新代次/目标”，底部导航每次点击先记录目标代次，再调用 `goBranch`；目标页监听自己的代次并调用现有数据刷新方法。
   - 刷新只重读数据，不销毁 `StatefulShellRoute` 分支、`PageStorageKey`、ScrollController 或表单 State；滚动、筛选、分页、日期、人员和草稿保留。
   - 通知、我的下属及下属工作浏览继续使用 `RefreshIndicator`，缺少显式入口的页面补 AppBar 刷新按钮；刷新失败保留旧内容和错误提示。
   - 写入成功后按领域失效相关 provider/刷新代次，避免关闭弹窗后仍显示旧数据。备选每次导航 `goBranch(initialLocation: true)` 会重置页面与滚动，不符合保留要求。

6. **负责人排序放在共享后端候选投影。**
   - `creationCandidates`/`dispatchCandidates` 增加稳定的位置角色权重：创始人、部门负责人、团队负责人、普通员工；同权重按姓名、ID 排序。
   - Flutter 组织树按返回顺序构建部门/团队分组，因此同组负责人自然在前；搜索只过滤结果，不重新排序。已选负责人列表仍使用用户保存/调整的顺序。
   - 备选仅在 Flutter 客户端排序会让 Web 与 App 不一致，不采用。

7. **首页序号是纯 UI 序号。**
   - 事件纪与任务看板预览、完整清单直接用当前 index+1，不写入数据库，不用任务真实 ID 冒充序号。
   - 序号作为独立左列，不参与渐隐；窄屏和放大字体仍保留可点行与正文空间。

8. **渐隐重影按字素边界修复。**
   - `resolveNameFade` 继续测量实际截断位置，但把“末个完整可见字素”之前的前缀与末字本身分开。
   - 渲染时前缀不包含末字，遮罩层只绘制该末字；完整显示路径不变。这样不改变测量、无障碍原文和行数，只消除重复绘制。
   - 增加针对中文、混排、放大字体的组件测试，断言截断时只出现一份末字且没有省略号/额外字符位。

9. **错误安全按“后端兜底 + 客户端统一展示”处理。**
   - 后端 `ApiAdvice` 增加未预期异常兜底，返回稳定错误码和中文通用说明；已有业务异常继续使用明确错误码。
   - 审计用户可见的校验/冲突文案，移除英文请求字段名和原始异常文本；内部细节只进入服务端诊断，不返回客户端。
   - Flutter 通过统一错误展示层把 `ApiException` 转为中文提示，不再在页面使用 `error.toString()`；网络、超时、权限、未找到、冲突、校验、会话失效保持可区分并保留重试/修改输入路径。
   - 管理端专属映射和文案清理不在本 change 处理。

## Risks / Trade-offs

- **软删除后旧客户端仍读取任务** → 共享列表/详情先在服务端过滤并返回 `TASK_DELETED`；发布顺序先后端再客户端，旧员工 Web 只做兼容验证，不新增入口。
- **待审申请与删除竞争** → 删除事务在任务行锁内重查 pending；有申请时拒绝，删除与申请决定只允许一个成功。
- **删除父任务影响子任务/日志/通知** → 保留外键与引用，统一用 deleted 投影和 `parentUnavailable`；不假设级联清理。
- **每日事项迁移语义变化** → 旧记录显式设为全天，旧客户端日期写入仍按全天；新增定时字段可选，避免破坏现有 Web 和测试。
- **定时跨日与公司时区边界** → 使用公司时区构造截止时刻，测试开始前、范围内、截止前、恰好截止、截止后及跨月/跨年。
- **导航刷新造成重复请求或覆盖筛选** → 刷新代次只触发目标页读取，读请求带账号/人员/日期守卫；失败保留旧内容，不重置本地状态。
- **刷新与未保存表单冲突** → 底部导航刷新不影响已打开表单的路由栈；表单草稿只在用户明确放弃或保存时变化。
- **错误审计范围大** → 先建立统一展示层和后端兜底，再按任务、日志、每日事项、标签、通知、登录、评论优先审计；测试用英文/技术错误样例防回归。
- **首页序号被误当成业务标识** → 序号仅 UI，使用无障碍说明“第 N 条”，并保持排序/点击不变。

## Migration Plan

1. 新增任务软删除字段及索引；字段可空，先部署后端过滤/详情兼容逻辑，再发布 Flutter 删除入口。
2. 新增每日事项 `all_day/start_time/end_time`；迁移旧行为全天、时刻为空，保留所有原字段与时间。
3. 发布员工 App 的标签入口、删除入口、时间表单、序号、排序、刷新和渐隐修复；员工 Web 仅验证兼容。
4. 回滚 App 不影响数据；回滚后端前需确认已软删除任务是否要恢复可见，避免已删任务重新出现。迁移本身不需要重写历史或清除业务数据。
