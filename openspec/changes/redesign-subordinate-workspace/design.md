# Design

## Context

现有reports已返回完整合法后代及managerId，person和日志/任务接口独立校验权限。主界面为原生JS/CSS和弹层栈，主题以莓色、淡粉和纸白为主。沿用现有设计系统、字体和焦点规范，重做信息结构而非更换视觉语言。

## Goals / Non-Goals

**Goals:** 真实可展开树、适配320/390的小屏专用人员工作页、身份/日期/返回上下文明确。

**Non-Goals:** 不修改组织、授予新任务详情权限、变更个人日志/日历范围、部署云端或做手机真机测试。全面“正常可见即可编辑基础资料”暂缓，本轮基础资料编辑仍仅业务责任方。

## Decisions

- reports按managerId构树，根为本人直接下属；必要结构异常仅在授权集合内安全降级，递归有去重保护，展开状态会话隔离。姓名、身份/职位及真实部门/团队分别呈现，不能用 positionName||teamName||departmentName 互斥回退而隐藏组织；无部门公司层显示公司层，不伪造组织。
- 人员页使用全屏弹层，顶部小身份卡及可折叠资料、日程/日志两个页签。日程默认月视图，可切日视图；月视图采用周一至周日网格、跨日连续条和+N入口，点击日期进入日视图。日视图为00:00至24:00纵轴/任务清单，全天区独立，复用P.calendar.monthWeek/dayCoverage/layoutDayEvents等纯投影算法，不使用全局本人过滤与状态。前后按当前模式翻月/翻天，日期选择可跳转，今天回当前日；公司时区裁剪，按整月网格/当天完整分页读取。日志为最新在前的短摘要日期卡片，每页10条可加载更多，点入详情阅读全文和评论。
- 仅允许reports中人员进入专用页，每次打开重新读取reports及person，业务内容再次由API裁决；筛选assigneeId与authorId服务端完成。权限变化报错时清空原内容，旧账号/旧选人响应由epoch/sequence丢弃，失败可重试。
- 自身日历、日志和任务表单不写入所选人员状态。任务/日志详情复用鉴权读取，父view.rebuild保留人员、日期及页签；以适配小屏的局部日历复用本人月/日设计，不切换本人主页面。
- 明确区分日程画布和任务详情：下属月/日/全天区不生成平移/端点控件，不绑定本人拖动处理，不提供任务表单按钮或画布上的独立调时入口。点击任务仍打开普通鉴权详情，不传播强制 readonly 标记；编辑、仅排期、进展、完成、重开、交接分别按当前用户原权限显示及服务端校验。拥有基础编辑权者和没有该权者分别验收，不能只验证一个上级账号。
- 共用算法接收展示模式而非隐式继承交互能力。下属月历与本人月历都按公司日期绘制日级跨度，午夜截止半开边界、零时长、跨周/跨月及 +N 保留；日轴继续按真实时段。待审投影与虚线沿用排期 change，普通详情仍有效版。完成状态在月历、日轴、全天区和清单均有可辨标签/样式，不能只在清单显示。

## Risks / Trade-offs

- [长名字和深层缩进挤压] → 节点分行显示职位/组织，固定展开按钮，320/390/1440截图测量。
- [日期边界/午夜多一份] → 读取当天候选后按公司业务日半开区间裁剪，点任务特殊处理。
- [旧响应串人或权限撤销残留] → 每请求序列与epoch校验；服务端错误清空内容，返回/重试重新验证。
- [共用未归档工作区] → 单独变更和指纹记录依赖，不宣称独立checkout。

## Migration Plan

无数据迁移。打包网页资源并更新本地预览，保留演示库。独立验证后再归档，后续云端发布另行处理。

## 验证衔接

既有 FAIL 报告仅对应其记录快照，保留原文。V-001/V-002、下属无拖动但详情保留现有操作、月历日级几何及待审虚线均由重新打开任务验收；不能复用旧“下属只读”或后续“下属可拖动”的检查结论作为新规划 PASS。实施后由 apply 更新 implementation-notes.md，再独立验证。
