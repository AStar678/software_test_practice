## Context

管理端当前是 `admin.html` 加根目录静态脚本：员工页只有 `employeeQuery` 搜索，`employeeNew` 收集资料后把新员工放入 `state.planDraft.newEmployees/placements`，必须转到“组织调整”填写完整计划并保存；停用和业务接管从“停用与接管”页进入，同样汇入组织计划。后端 `OrganizationService.createEmployee` 已通过现有完整计划校验原子建号并返回一次性初始密码，但缺身份证号、独立筛选和独立离职契约。任务历史已能按任务 ID 读取，但任务软删除字段由员工 App change 引入，管理端尚未识别 deleted 状态。

身份证号、员工增删改、离职和已删除任务历史都会影响权限、PII 或审计；管理端错误文案还直接使用接口 `message`，部分静态说明是防御性/技术性文字。动机见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- 在员工页提供可组合筛选，同时保持现有四层组织、位置和账号规则。
- 让独立入职直接完成建号与位置保存，但不绕过既有组织计划原子校验。
- 用独立离职向导复用现有责任盘点、交接、接管、申请处理和会话撤销。
- 只让管理员受控读取身份证号，并在列表脱敏、App/员工投影不可见。
- 在任务历史中识别已软删除任务及其完整历史。
- 统一管理端错误展示并清理无业务价值的说明文字。

**Non-Goals:**

- 不改变四层组织、固定创始人、单负责人、必填展示职位、手机号唯一和审核规则。
- 不新增第二套任务交接、业务接管或审核引擎。
- 不放宽管理员员工业务权，不把管理员加入负责人候选或审核链。
- 不实现员工 App 的任务删除、每日事项时间、首页序号、刷新或渐隐，这些由独立 App change 负责。
- 不把身份证号用于登录、组织推导、任务候选或员工资料展示。

## Decisions

1. **员工筛选在现有管理目录投影上组合执行。**
   - `/admin/employees` 增加 `q`、`departmentId`、`teamId`、`placementType`、`active`、`positionId` 查询参数；`q` 匹配姓名、部门名和登录手机号。
   - 服务端先构造现有管理员目录，再按同一条件过滤并计算 `total`；列表仍按现有稳定规则排序，不做分页迁移。
   - 选项由已加载的 `organization` 与 `positions` 生成，不新增伪造目录；筛选失败保留旧列表并显示重试。
   - 备选只在浏览器过滤会让总数和其他管理端调用不一致，不采用。

2. **身份证号放独立管理员专用表，不进入公共员工投影。**
   - 新增 `employee_identity_documents`（或等价专用表）：`organization_id`、`employee_id`、规范化 `id_card_no`、`row_version`、时间戳；公司内非空身份证号唯一，外键指向员工。
   - 只有管理员员工详情/编辑接口读取完整值；员工列表在管理员服务层脱敏，普通 `Access.employeeDirectory`、任务候选、通知、日志、分析、审计和 App DTO 不查询该表。
   - 校验 18 位格式、出生日期、顺序码和校验位，末位 `x` 规范为大写；变更记录只保存“字段已更新”或脱敏值，不写完整号码。
   - 入职必填；既有员工未录入时明确显示未设置，管理员可后续更正。备选把身份证号加在 `users` 公共行上容易被现有宽查询带出，不采用。

3. **独立入职复用当前单员工原子建号能力。**
   - 员工页“入职”收集姓名、手机号、身份证号、hireDate、组织身份、部门/团队和展示职位，直接调用现有 `POST /admin/employees` 扩展后的契约，不再先写入前端 `planDraft`。
   - 服务端仍构造一份只含该新员工的最小计划并复用 `OrganizationPlans.save` 的锁、组织版本、位置唯一性、初始密码和审核刷新；身份证号在同一事务写入专用表。
   - 若最小计划需要修改既有人员/单位（第二创始人、占用已有负责人、跨部门团队、负责人替换、删除单位等），服务端拒绝并返回“请到组织调整”，不静默改动既有位置。
   - 成功后返回一次性初始密码并按新组织结果刷新员工页和组织树。前端不保存临时入职草稿到组织调整。
   - 备选直接插入 `users/placements` 会复制组织不变量校验，容易出现与组织计划不同的非法结果，不采用。

4. **独立离职向导生成受限离职计划，而不是自由编辑整张组织计划。**
   - 新增 `POST /admin/employees/{id}/offboard`，请求只接受员工 ID、离职原因、岗位继任/单位负责人安排、业务接管项、未发布申请处理及当前版本；不接受任意部门/团队/其他员工位置编辑。
   - 服务端读取现有责任盘点，构造仅含 `deactivateEmployees`、`businessTransfers`、`cancelUnpublishedRequests` 和必要继任位置的最小计划，复用 `OrganizationPlans.save`、`EmployeeDeactivations`、`BusinessTakeovers` 完成任务交接、业务接管、会话撤销、待审刷新和历史记录。
   - 若员工是单位负责人，离职请求必须包含合法继任；若仍是其他结构冲突，拒绝并提示转组织调整。固定创始人拒绝普通离职。
   - 任何版本、待审、截止、接管人、继任或并发失败都拒绝整次离职，不部分停用。
   - 备选让前端自由拼组织计划会重新暴露“员工增删改与组织调整混在一起”的问题，不采用。

5. **管理端员工列表与详情使用同一身份投影边界。**
   - 管理员列表返回脱敏身份证号和筛选所需位置字段；详情返回完整身份证号仅供管理员核对。
   - 员工编辑只允许管理员修正资料/身份证号，不允许员工本人或业务上级读取；修改身份证号使用版本校验并触发审计字段事实。
   - 普通员工搜索、任务候选人、日志、通知和统计不增加任何查询分支。

6. **已删除任务历史复用现有历史查询并增加删除投影。**
   - 依赖 App change 在 `tasks` 增加软删除字段及员工端过滤；管理端 `/admin/tasks` 增加 `deleted` 筛选，行投影增加 `deleted`、`deletedAt`、`deletedByName`。
   - `/admin/tasks/{id}/history` 对已删除任务继续读取版本、申请、审核、改派、交接、业务接管和删除记录；历史入口只读，不重新开放任务详情/评论/写操作。
   - 管理端任务历史列表和详情明确区分已删除和正常任务，不能把删除任务从历史中隐藏。
   - 若 App change 尚未实施，Admin change 不应先应用；任务软删除契约是前置依赖。

7. **管理端错误走统一安全展示，文案清理保持业务上下文。**
   - 复用 App change 的后端安全错误兜底；管理端增加 `safeAdminMessage(error)`，按错误码/状态映射中文说明，未知错误显示通用失败，不直接渲染 `error.message`、异常对象或技术字段。
   - 对 `admin.html` 当前可达界面的静态文案审计：删除 AI 式、原型/开发解释、防御性“不会/仅为/为了避免误解”文字；保留字段名、空态、校验、危险确认、待审/冻结/失权、接管原因和历史来源。
   - 清理只针对静态产品文案，不改用户输入、公司信息、任务历史、审核意见或真实业务内容。

8. **管理端流程继续使用现有服务端授权。**
   - 新筛选、入职、离职和历史查询均要求现有独立管理员能力；管理员仍不取得员工业务权限。
   - 入职/离职服务不绕过 `requireAdmin`、组织版本、公司锁、初始密码、会话撤销和任务审核链刷新。

## Risks / Trade-offs

- **独立入职与完整组织计划并发** → 两者都走公司锁和计划版本；入职最小计划与当前组织不一致时拒绝并重新读取，不静默覆盖。
- **负责人替换仍需要多人调整** → 独立入职只允许不改变既有负责人/单位的结果；冲突明确转组织调整，避免入口分裂但规则不一致。
- **身份证号是敏感 PII** → 专用表、管理员专用查询、列表脱敏、审计不含完整值；不在日志和错误信息中回显。当前项目没有独立密钥管理，不引入无法运维的加密方案。
- **离职仍可能产生复杂结构变化** → 离职服务只接受受限字段，内部复用完整计划校验；单位负责人继任缺失时拒绝。
- **已删除任务依赖 App change** → Admin change 后实施；若任务软删除字段不存在，历史/筛选测试失败并阻止发布。
- **错误文案过度泛化** → 保留错误类别和可操作下一步；只隐藏技术细节，不把所有失败压成同一句。
- **文案清理误删业务说明** → 只审计静态产品文案，保留字段、空态、校验、危险确认和历史内容；按页面清单逐项验证。
- **筛选在内存执行随员工规模增长** → 当前管理端返回完整目录且规模有限，先保持行为一致；未来数据量增大再引入服务端分页。

## Migration Plan

1. 先完成 App change 的任务软删除迁移和员工端过滤；Admin change 不重复创建删除字段。
2. 新增员工身份证专用表及必要唯一索引；旧员工无记录时保持空态，不猜测号码。
3. 部署管理端筛选、独立入职/离职后端契约和管理端页面；管理员仍通过现有认证进入。
4. 发布已删除任务历史投影和管理端筛选，验证旧通知/申请/日志链接不崩溃。
5. 回滚管理端 UI 不会删除身份证数据或离职历史；回滚后端前确认新入职账号和离职记录已按业务保留，不执行物理删除。
