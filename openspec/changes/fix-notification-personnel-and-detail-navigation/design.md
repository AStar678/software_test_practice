# Design

## Context

见 proposal.md。后端 ReminderService 产生 task.reminder_N/task.overdue，WorkspaceService 的分类仅匹配 reminder./task.deadline.。通知投影只凭 requestId 展示申请入口，而 TaskService.canReadRequest 才对应真实申请权限。前端 rememberPeople 只插入；人员芯片从 role/dept 与 raw 取字段。弹层已有栈，但普通头部关闭清空全栈，下属日程没有继承逐层返回标识。

## Goals / Non-Goals

目标是修复投影及导航一致性，复用当前对象与申请权限。无结构迁移、不扩大普通接收人申请/diff 权限、不改审核路由、提醒触发或拖动业务规则；不连接手机、不自动上线、不归档旧变更。

## Decisions

1. 分类和用途共用真实提醒事件识别，保留旧前缀兼容；服务端过滤与行投影复用此规则。
2. 通知增加 canOpenRequest 能力，使用现有 TaskService.canReadRequest 无副作用探测，revoked/受限内容无入口。前端仅在能力为真时提供原申请入口，合法原结果摘要继续展示；不开放普通接收人完整申请作为替代修复。测试原申请而非后续申请。
3. 人员映射更新已有条目，合并已知原始字段并以显式有效值覆盖，缺省姓名摘要不覆盖身份；重载先建立完整人员目录，再合并参与者。不能从职位文字推算身份，也不把团队当部门。
4. 下属工作弹层声明独立逐层返回上下文，子层继承；保留通知导航既有语义。原工作视图在返回重建时重验权限，并恢复日期、模式及滚动位置；session/请求序号防止迟到响应污染。
5. 置顶入口复用本人日历投影资格而非普通可见性，点击也做相同客户端防卫，后端原权限继续兜底。
6. 文案以员工实际加载资源逐页清理，移除实现解释与重复规则，保留简短操作提示和业务限制。日志保留冻结状态/时间，移除独立编辑权限行。

## Risks / Trade-offs

- 权限能力可能过时 → 点击仍由后端实时鉴权；不恢复历史通知受限提议。
- 新能力增加查询 → 同页按申请去重探测，使用既有批量投影缓存且不跨请求缓存权限。
- 弹层返回与异步读取竞争 → 保留 session epoch/序号检测，对返回重读及切人迟到响应回归。
- 文案清理误删业务信息 → 记录清理清单并检查冻结、错误、结果与统计来源。

## Migration Plan

正常构建打包共享 Web 资源即可，无数据库迁移。专项测试使用独立临时数据库及真实桌面 Chrome 的 320/390/1440 视口。上线另按用户请求执行。
