## Goals / Non-Goals

**Goals:** 用同一套字段资格完成预览、提交和审核生效；统一浏览组件时显式传递人员、返回状态和只读模式；以统一接口和无损数据迁移形成交付前契约；把实际业务变化放到详情首屏。

**Non-Goals:** 不引入通用角色系统、全公司可见即可编辑、申请接收人普遍读取差异、新的后台历史模型或新的审核路线。不修改原生 Android 和套壳资源、不构建 APK、不部署或推送；不为尚未交付的旧客户端增加版本兼容层。文案清理不改变真实任务、日志、评论或历史文本。

## Decisions

### 1. 服务端统一通知语义，并分别裁决任务、申请与审核动作

分类函数显式识别当前生成的 `task.reminder_20/10/5` 和 `task.overdue`，覆盖当前仍实际使用的事件名，元信息过滤、总数、列表投影和详情用途共用映射。不重命名已持久化事件、不重投递旧消息；当前有权且未到期的待审审核能力仍优先决定“需我审核”。

通知 DTO 增加 `canReadRequest`，与 `canReview`、普通对象/历史只读跳转分开；使用 `TaskService.canReadRequest` 的同一规则并批量化读取，避免逐条探测造成 N+1。权限真值取自服务端当前申请关系，不取决于 requestId 是否存在。原申请不存在或不属于通知绑定对象时隐藏入口，显示简短“原申请不可查看”。不能把同一任务的最新申请替换进旧通知。申请人和对应审核人继续从标准申请接口读取各自允许的投影；其他合法结果接收人仍读通知允许的结果摘要，不新增申请读取权。

通知展示增加可选结构化 `eventResult` 和 `changes`（字段标签、旧值、新值/简短结果），由真实事件、已授权快照/申请生成；它仅包含该通知本来允许展示的变更摘要，不复用审核专用 diff，不扩大待审提议可见性。历史消息缺少可证明数据时保留已有合法摘要，不靠字符串分割猜测前后值或编造结果。所有新增字段在撤回、送达屏蔽、失权及评论删除时同步裁剪。

详情按“事件结果→具体变化→任务名称与通知时间→简短申请状态”组织；主按钮优先当前审核，其次有权原申请，再其次关联对象，其他导航低强调；同对象仍只有一个入口。删除消息、撤回通知、申请人撤销申请分别命名并放“更多”，保留独立版本/期限和确认，不混淆通知撤回与业务撤销。采用有键盘和焦点恢复能力的菜单，不为隐藏次要按钮增加新业务流程。备选是继续使用长 summary 和 requestId 推断按钮，无法解决信息重复及无效跳转，故不采用。

### 2. 信息编辑以字段权限为核心，混合变更只建一个申请

普通任务详情仅保留一个“编辑任务”信息入口，表单按服务端 `editableFields` 投影显示合法字段；仅有排期权者进入同一入口的排期子集，不再并列基础编辑、调整排期、更新进展三个信息入口。完成、专用交接、重开仍独立。`progress` 和 `reschedule` 仍可作为独立业务命令，不新增版本兼容分支。

| 当前身份/上下文 | 普通资料字段 | 当前文字进展 | 负责人列表及顺序 | 完成、交接、重开 |
| --- | --- | --- | --- | --- |
| 当前有效负责人 | 可申请 | 可申请 | 不可，除非同时是创建者/正式接管人 | 依原专用资格 |
| 创建者在任／正式接管后接管人 | 可申请 | 仅同时为有效负责人时可申请 | 可申请 | 依原专用资格 |
| 其他正常查看者 | 仅既有精确排期 | 不可 | 不可 | 依原专用资格 |
| 下属浏览路径（包括嵌套详情） | 不提供 | 不提供 | 不提供 | 不提供，唯一写能力为评论 |
| 通知历史只读 | 不可 | 不可 | 不可 | 不可，也无评论权 |

普通资料字段包含标题、说明、历史已有完成标准、紧急程度、开始/截止、共用标签和父任务；原创建者、创建时间、组织、执行轮次及执行状态不可作为普通字段直接写入。创建仍不新增完成标准。用户的“其他可以改”解释为合法可编辑业务资料，不含来源元信息和专用状态命令；保留已有进展仅有效负责人可写规则。

扩展 `change` 接受可选 `progressNote`，资料和当前进展基于同一有效版本形成一个完整提议。有效负责人无负责人管理权时，省略 assigneeIds 保留原有列表；完整载荷可接受与有效列表完全相同的数组，但换人、增删、重排一律拒绝。若更新进展，批准或创始人合法直接生效时按既有进展语义将待开始置进行中；字段和进展同事务生效，只生成一个申请及一条同事件汇总通知，并保留所需进展记录/字段审计。仅改资料不改变执行状态，清空进展按当前文字编辑语义保留可审计变化，不直接完成任务。

生效与待审路线刷新必须根据 base/proposed 实际差异重新裁决：修改负责人只看创建者/正式接管资格，普通资料看此资格或有效负责人，进展仍看有效负责人，纯排期保留正常查看资格。不能通过把所有 change 都按“纯排期”或“责任方”处理绕过/误拒。申请期间失去所需资格必须阻断；单待审、冻结、截止、ETag、幂等、父关联和有效选人校验保持。重放仍重验身份。

审核界面按后端授权 diff 默认只显示真实变化，每项字段名、上方原值、下方新值；负责人的顺序变化和多标签集合变化清楚可辨。创建没有旧版本时显示待创建内容，不假造旧值。申请人仅看自己的提议和结果，不拿到专用 diff。提交成功回读已保存申请的当前审核人，不用预览猜测；免审显示“已生效”，路线阻断简短说明，不显示虚构审核人。隐藏员工端“当前业务责任方”和普通详情固定 reviewerId，不删除服务端接管数据或后台历史。

备选是前端放开字段但服务端仍只允许责任方，或拆为资料和进展两次申请；前者不能工作，后者违反一次提交要求，故均不采用。

### 3. 下属浏览只读上下文沿导航链传递，恢复精确来源

拆分人员资料卡与工作浏览页。资料卡展示必要组织/联系方式字段及日程、日志入口，去掉公司行；本人页面也去掉公司行。工作页复用本人月/日呈现、底部日期清单与日志阅读组件，通过 `subjectId` 限定数据，通过 `readOnly` 限制动作，不能借复用把下属任务写进本人日历或本人日志集合。

为每一层 sheet 保存不可变来源快照：会话 epoch、人员 ID、页面类型、页签、公司日期、月/日模式、日轴方向、已加载范围/分页、滚动位置和触发焦点。复用现有 sheet 栈和 rebuild 约定，避免 closeSheet 清空全栈；详情返回只弹一层。关闭按钮、返回/Esc、遮罩以及评论提交后的重建均回到原人员上下文。重新检查权限时允许刷新数据，但不重置日期/人员；失权清空正文，旧请求用 epoch+人员+查询序号丢弃。

下属上下文传入任务、日志、父子任务及关联任务详情，普通信息与专用业务按钮均不生成，置顶也不生成；私人标签及颜色覆盖按全局移除处理；action 分发和表单打开/提交再次检查当前只读上下文，防止残留事件或旧草稿触发业务写请求。可发表评论、按原作者权限编辑/删除自己评论，均由服务端对象正常查看权校验。

这里是用户确认的 Web 下属浏览操作模式，**不以可伪造的来源标记充当账户权限边界**：服务器依然按独立正常入口的字段权限鉴权，知晓 taskId 不产生新权力；同一用户从自己的独立授权入口可办理自己有权的操作。验收同时检查下属路径不发送非评论写请求，以及直接业务 API 仍拒绝越权字段。备选是全局撤销管理者调时或创建者编辑权，会改变其他入口及原生客户端而超出本次确认，故不采用。

该决定明确替换 `Hierarchical subordinate workspace`、`Subordinate calendar month and day views`、`Calendar dragging by presentation`、`Reschedule every visible active task` 中“下属详情不强制只读”的旧口径。

### 4. 用完整真实区间判断日内拖动资格，月拖动使用独立确认草稿

将片段可拖动判断与 `canRescheduleTask` 分离：本人普通定时任务的完整区间须落在当前公司业务日 `[00:00, 次日00:00]`，零时长须属于当日；午夜结束允许作为当日真实末端。历史全天任务、完整覆盖一天的任务以及起止不全在当天的截取片段，在横向和纵向日视图均不生成 move、端点或键盘调时绑定；整日覆盖优先排除，即使完整区间恰好一天。跨日任务首尾的部分片段也从详情精确调整，避免片段拖动改变整条任务。

普通日内任务保持一小时差量、原分钟、真实端点和零时长行为。月历整条/真实端点仍按天，续接抓取仍按实际命中日期算差量，和日视图禁止截取片段拖动不是同一规则。全天/续接普通点击可进详情；没有额外画布调时按钮。

`openScheduleChange` 改为独立轻量确认草稿，保存 taskId、拖动起点 rowVersion、有效版旧排期、提议新排期、reason、mutation slot、来源导航快照。只展示旧/新完整排期、原因、提交；必要的审核结果在提交后提示。日内拖动复用同一弹层以避免两个保存实现；详情精确编辑继续用统一编辑表单。打开弹层回读版本，不把旧拖动差量无提示套到新版本。取消和失去捕获不写入；网络失败保留原因，重试同一载荷复用幂等键，提交前再校验权限/状态/版本。提交后的虚线投影、普通详情有效版及结果恢复保持既有语义。

这是明确替换全天区可拖动的设计变更，不是删除全天任务调整能力；替代入口为独立正常详情。备选是给跨日片段增加更长警告仍允许拖动，无法消除误改整条任务，故不采用。

### 5. 日志有序标签采用任务已验证的数据模式，统一集合接口

新增下一号 Flyway 迁移（当前最新 V28，因此预期 V29；实施时若已有更新须顺延），创建 `work_log_tags`，按组织、日志、标签关联并保存 ordinal、名称/颜色快照，约束同日志标签唯一和顺序唯一。回填已有非空 tagId 为第零项，空为无记录；回填校验后移除旧日志 tag_id 及其相关约束，集合为唯一数据来源，不增加首项双写。保留原日志 ID、作者、业务日期、正文、首次创建/删除时间及冻结窗口；迁移不通过用户写接口重建日志。

日志接口统一输入 `tagIds`、输出 `tagIds`/`tags`，创建省略标签为零项，编辑省略标签字段保留整个集合，显式空数组清空；重复 ID 或不支持的单标签字段按统一请求校验拒绝，整次不写入正文等其他字段。不保留日志 `tagId/tag` 兼容读写；日志列表、详情、首页近期日志和下属日志读同一集合投影并批量加载。只允许本公司共用标签，跨公司/无效引用拒绝，已移除私人标签的旧标识不可引用；已有已删除标签保留原顺序和快照，可移除，移除后不能新挂回。目录改名改色更新当前显示，历史审计不重写。

从现有任务多选色块提取只管理选择和渲染的组件，任务、创建日志、编辑日志共享；任务/日志草稿、保存目标与权限保持独立。选择按加入顺序稳定持久化，取消再选视为新加入，不以目录名称排序重排。日志详情不再显示编辑权限行，作者可编辑由按钮表达，冻结状态保留简短提示。现有三天补写、唯一日期、首次创建24小时冻结及评论规则不变。

备选是只把前端 select 改为多选但继续保存一个 tag_id，会丢数据；复用任务版本表则会错误引入日志审核语义，故采用独立日志关联表。

### 6. 人员显示、任务颜色、置顶及历史采用统一安全投影

人员摘要统一合并规则：同账号同组织按 ID upsert，字段缺省不覆盖已有完整值，显式 null 可以清除已撤销组织字段；只有真实 placementType/role 能确定身份，positionName 只作展示。姓名摘要不得制造 employee 身份并永久阻挡完整资料更新。组织/资料版本变化使相关缓存失效并回读，旧会话/旧查询响应不能倒灌，手机号邮箱不进入通用缓存。展示公司层/真实部门/团队，缺失数据安全占位，不把“部门负责人”职位当成组织身份。

所有任务呈现复用同一颜色解析：tags 稳定有序首项（含合法保留的已删除快照），无标签为默认粉色；修复 mapTask/日程/下属渲染对单 tag 的依赖。全局移除私人标签及私人颜色覆盖，不再读取 personalTag 或按用户覆写底色，不会因为任务多标签而给任务多个底色或改动标签顺序。

置顶资格用本人正常日历范围判断（当前有效负责人、正常已发布、有正常查看权，含已完成任务），与 canEditTask 分开。详情、action 和已有服务端 pin 写入口一致重验，非日历任务不显示按钮，旧请求拒绝；下属只读上下文无论是否同时本人负责均不提供。个人 pin 是本人排序设置，不属于私人标签；已有个人置顶数据不据此大规模删除。

员工详情移除 records 时间线，只取当前 progressNote 和本人有权的相关申请/审核意见；不把 records 替换成另一条完整历史时间线，也不删除任务进展持久记录。员工投影同步移除历次 records 字段，完整后台历史 API 的管理员鉴权不变。

### 7. 完整移除私人标签模型，不将私人内容公开化

用户最新确认优先于原提案中的“已有私人覆盖继续优先”。移除 `潘多拉-标签评论.js` 私人标签管理/范围文案/保存事件、任务 personalTag 读取与色彩优先级，标签管理只维护公司共用项；创建标签请求只用名称和颜色，不保留 personal scope。移除 `TaskController` 的 personal-tag 路由、`TaskService.setPersonalTag`、`Tags` 私人选择/所有权分支、批量查询及 DTO 的 personalTag/canCreatePersonal 等字段。删除旧路由后直接请求无可用写操作，不提供兼容重定向。

在日志集合迁移之后用下一号新增迁移清理 V27 个人模型：先检查私人目录项是否异常被任务单标签列、任务标签集合或日志集合等共用关系引用；若有则报告明确阻断，不能把私人名称自动转为共用数据。合法结构下删除个人任务覆盖关系和私人目录项，移除 `personal_task_tags` 及 tags 的 owner_id/owner_scope、相关外键/索引，恢复公司内共用名称唯一约束。保留全部共用标签及其已删除快照、任务/日志正文、原创建信息、业务审计和个人置顶；历史迁移 V27 不改写。迁移验证覆盖存在私人目录/覆盖的升级库与全新空库，不以当前演示库恰好无私人数据代替。

既有检查中“可创建私人标签/覆盖优先”的断言按新规则替换；验证所有用户都从同一任务共用首标签取得底色，私人旧ID和请求被拒绝、公共/管理界面无私人入口，清理不生成新任务审核或改写有效排期。备选是仅隐藏入口但保留后台模型，不能满足统一移除，故不采用。

### 8. 管理手机号只进入管理专用 DTO，静态文案逐页清理

在 `OrganizationService` 的管理员员工列表与详情路径构造管理专用投影，从当前用户的 `login_phone` 取得完整 `loginPhone`，不从可能分离的联系电话推断。名单及详情/编辑弹层均可核对，更新成功后回读真实登录号；空缺显示“未设置”，不伪造。既有 phone 写入契约、规范化、唯一登录键、改号撤销会话保持。

保留 `Access.employeeDirectory` 等公共目录的隐私裁剪，管理投影受 requireAdmin、当前会话及同组织约束，不能让新增字段进入候选、任务 participants、通知、普通缓存或审计。此处显式替换 `Account password lifecycle` 及 `Role-scoped visibility` 对管理响应不得读取的旧条款；本人和实际管理链详情的手机号读取规则继续有效。备选是把 public directory 的 SELECT 加 phone，会让普通接口泄露，故不采用。

文案按当前可达页面和二级弹层逐项检查，覆盖员工五页、通知、申请、个人/下属资料、任务/日志表单、账号页和 PC 管理端。仅改静态模板和安全兜底措辞，保留字段标签、失权/冻结、错误重试、危险操作确认、统计真实范围/生成时间及简短来源。不用关键词过滤业务正文；不将“隐藏内部责任概念”实现为删除接管权限或历史。

## Risks / Trade-offs

- [负责人扩大资料权影响待审生效检查] → 按真实差异统一权限函数，覆盖负责人被移除、仅列表换序、混合进展和正式接管；提交及批准均测试。
- [下属只读模式在嵌套详情丢失] → 来源上下文沿父子/日志关联/评论重建传递，测试重叠身份、全部退出方式和残留旧草稿；服务端正常入口仍独立鉴权。
- [通知结构化变化泄露审核专用数据] → 只投影既有合法通知摘要信息，和 canReadRequest/diff 分离；评论撤权、撤回及未送达屏蔽一起验证。
- [私人数据被误当共用标签公开] → 迁移预检查共用引用，异常明确阻断；仅清理个人目录/覆盖，不转公开，不删除共用快照及业务审计。
- [日志迁移丢失已有引用或重置冻结点] → 回填校验后才移除旧列，集合与正文同事务保存，校验条数/顺序/首次创建时间。
- [复用组件污染本人数据] → 查询 subjectId 与本人页面状态独立存储，复用渲染而不复用可变筛选；全量分页后投影。
- [管理手机号进入通用缓存或日志] → 管理专用 DTO，测试跨组织和普通 DTO 不含 loginPhone/phone，审计只存字段变化类型而无明文号码。
- [旧专项脚本仍要求全天拖动或下属详情可编辑] → 更新这些已被本次确认替换的断言，保留历史报告原文，以新契约独立验证，旧 PASS 不作当前证据。

## Migration Plan

1. 先在隔离库演练连续新增的日志集合迁移与私人标签清理迁移，分别验证含私人数据的 V28 升级及空库建库；比对日志标识、集合、日期、首次创建时间、冻结点和业务历史，禁止改旧迁移。
2. 后端与员工/管理 Web 一起采用新集合契约，更新白名单打包及当前检查脚本；记录原生 Android 后续需适配日志集合、共用标签与员工历史投影，不将未适配原生端计作本次验收。
3. 用真实认证、事件 worker、数据库和构建后静态资源完成专项 API、浏览器及 Maven 检查。320/390/1440 宽度验收只读路径、差异堆叠、轻量确认和多标签；不把 Web 结果写作 Android 通过。
4. 若需回退，使用演练过的数据库备份及对应前后端构建成套恢复；不能把已形成的多标签静默降为单项。新增迁移不提供破坏性在线降级脚本，不为回退维护日常双写兼容层。本工作流不执行发布或回退。
