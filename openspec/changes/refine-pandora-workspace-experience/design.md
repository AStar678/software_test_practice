# Design

## Context

员工 Web 使用原型脚本和后端接入脚本组合页面，后端使用 Spring Boot、MySQL 和 Flyway。首页的实际入口在 `潘多拉-工作区接入.js`，每日事项使用独立的 `/daily-items`。公司月历已有连续滚动和排期确认。员工工作页当前对日志使用分页列表，`/work-logs` 已支持按授权作者和业务日期查询。任务表单已在完整结果上过滤、排序、分页，月历置顶由后端保存。演示库已有显式目标、身份标记和稳定记录键。

## Goals / Non-Goals

**Goals**

- 复用日历视图的样式和滚动机制，按入口隔离业务数据、操作及浏览状态。
- 用真实日期、权限和持久化结果贯通首页、日志、员工资料及演示环境。

**Non-Goals**

- 范围限员工 Web、相应管理端字段、共用后端与演示数据。安卓原生、套壳和 APK 独立交付。
- 节假日是日历标记。考勤、薪资、任务调度和公司级自定义假期维护属于独立业务。

## Decisions

1. **共享月历外观，按入口提供不同内容。** 从 `潘多拉-日程视图.js` 提取或复用月份布局、日期格、样式变量、密度控件和日期锚点逻辑。首页使用 `潘多拉-每日事项.js` 和日期计数，员工日志和员工日程分别按授权人员及月份查询，公司日程继续投影任务。每处各自保存锚点和滚动偏移。将公司视图整体复制到首页会同时带入任务条、审批和拖动，难以守住入口边界。首页两张上方卡片保留独立滚动，事件详情以完整正文和真实发布时间为主，同层可切换其他公告，任务详情沿用原鉴权与操作，补充本人派发时间和更新时间。两个首页弹窗均用全高详情承载完整信息，关闭恢复对应卡片焦点。员工日程与日志共享有限窗口补载与滚动锚点，日程月格只呈现本月日期，跨月任务仍在实际覆盖日呈现。
2. **公司日历与每日事项共用年度节假日接口。** holiday-cn 每日检查国务院公告。服务启动后自动检查北京时间当年和次年，每五分钟检查缓存，成功及未发布结果缓存一小时，故障时保留最近成功结果并缩短重试间隔。按年浏览时共享缓存，按实际日期归入次年公告中的跨年安排。打开的日历约每五分钟更新标记，页面恢复可见时检查缓存，保留日历位置、事项数量和任务操作。上游只接收年份，来源地址由部署配置提供。 [holiday-cn 数据源](https://github.com/NateScarlet/holiday-cn)
3. **表单置顶与月历置顶分别持久化。** 在任务服务增加表单专用置顶读写，以组织、账号、任务为唯一键，重验本人创建或有效负责及正常表单可见资格。查询先取合法筛选结果，再按表单置顶分组、应用现有列比较器，最后分页。合并现有月历置顶会把两处排序与资格绑定；按页置顶会使后续页结果无法移到前面。
4. **在日志新建事务内保存关联引用。** 日期切换时请求预览，提交时由服务端用作者和业务日重新求值。任务按公司时区的半开日区间和当前有效排期匹配，排除仅提案覆盖的日期。分别保存任务与每日事项引用并按真实标识去重，与日志保存、幂等及审计一起提交。日志详情逐对象投影权限，任何非作者的载荷省略每日事项引用及其计数。与实时重算相比，保存引用可避免日志编辑或后续排期变化悄悄替换原关联。删除后重建按新建规则取引用，沿用原冻结起点。存量单任务关联作为已有引用兼容读取，存量日期和创建时间保留。
5. **用日期字段维护入职信息。** 在员工存储新增可空公历日期，管理端负责登记和校验，授权详情与本人首页由后端按公司日期统一计算。资料卡用真实组织字段组成面包屑，员工目录继续按真实关系展开。账号创建时间无法代表实际入职日期。
6. **复用本人排期确认，扩大拖动的可见范围。** 在 `潘多拉-日程视图.js` 中区分长按候选、已抓取和取消。触摸先滑动可正常滚动，抓取后以指针捕获和浮层展示排期。月历边缘滚动时持续按指针命中的公司日期计算目标，日轴仍使用原小时步长。保留现有月历端点语义、权限和服务端版本复核。支持时调用一次 Web 震动，始终显示可见反馈。 [W3C Vibration API](https://www.w3.org/TR/vibration/)
7. **把通知常用筛选前置。** Teams 将未读等常用项放在顶部并提供更多筛选，Slack 将常见类别与详情密度分开。采用「全部」「未读」「需我审核」快捷入口，独立保留已读状态、业务类别及精简/完整密度设置。快捷未读和需我审核分别更新自己的维度，「全部」同时清空两维。保持后端现有业务分类、组合过滤与分页，返回详情后重新同步可见项。 [Microsoft Teams 活动源](https://support.microsoft.com/en-us/teams/notifications-settings/explore-the-activity-feed-in-microsoft-teams) [Slack Activity](https://slack.com/help/articles/19693583638803-Get-your-work-done-from-the-Activity-view)
8. **用一条演示故事串起四层角色。** 在 `DemoSeed` 中围绕虚构企业的产品上线与市场推广组织业务，创始人定目标，部门负责人拆分里程碑，团队负责人分派审核，员工执行和补写日志。用产品部及市场部各自的真实组织层级展示可见范围，并用同主题的工作批次覆盖分页量和边界。相比把演示记录全换成静态截图，这条链路能用各账号实际操作。

## Risks / Trade-offs

- 月历滚动可能抢占页面或卡片手势 → 复用原生滚动，记录模块焦点与锚点，覆盖窄屏、短屏和键盘操作。
- 快速切换日期、员工或账号可能接收旧数据 → 为每个请求绑定会话、人员和查询范围，切换或失权时清理已缓存私有内容。
- 自动关联与编辑并发 → 提交以事务内权限和数据为准，已有日志继续按版本及冻结规则保护，日志关联读取不公开源对象。
- 浏览器震动受设备能力和设置影响 → 视觉抓取反馈始终启用；在支持震动的浏览器单独验证实际反馈。
- 演示数据调整可能覆盖既有业务 → 只经显式匹配的演示库身份和清单执行；验证重复运行及普通库保护。

## Migration Plan

通过新 Flyway 迁移增加可空入职日期、表单置顶和日志关联。保留现有月历置顶、日志单任务字段、日志日期及冻结时间；旧记录读取时兼容既有引用，历史日期没有足够依据时保持空值。先验证空库和存量库升级，再启用新 Web 入口并在显式演示库运行版本化准备流程。回退应用版本时保留新增数据结构及数据，回退前核对旧应用的日志写入行为与新引用读写兼容性。
