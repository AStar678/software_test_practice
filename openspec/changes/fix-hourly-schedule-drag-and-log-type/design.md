# Design

## Context

动机见 proposal.md。当前 a7b092d 的实现来自 c1d6073：月历按日格宽度/24换算小时、按小时占比绘制窄条，本人和下属画布共用拖动绑定；日轴为小时步长。独立验证 FAIL 已记录纵向全天区无手柄。用户现已确认月历按日显示和操作、下属画布不拖动、详情沿用现有权限；既有实施记录和验证报告描述历史输入，保留原文。

## Goals / Non-Goals

**Goals:** 用匹配视图尺度的交互替换旧统一小时方案；明确显示、画布拖动和详情权限三者边界；统一已发布任务的待审虚线和位置；保留日志字体、HTTP兼容及审核机制。

**Non-Goals:** 不扩大任务基础资料/负责人编辑权，不将拖动入口条件变成仅负责人服务端权限，不改进展/完成/重开/交接规则，不跳过原因/审核，不新增数据迁移，不改已归档日志规划，不默认发布或做手机真机测试。

## Decisions

### 1. 月历按日显示及调整，日轴按小时

月历使用公司日期覆盖而非小时 left/width：部分日覆盖占一个日期格，跨日按占用日期连续绘制，午夜截止不包含次日，零时长显示明确点任务但保留原零工期。跨周/月分段保留续接标识。标题/日期置于日级框内，小屏裁切可回读完整提示/详情，不为小时偏移挤压标题。下属共用同一纯几何规则。

本人月历整条平移按公司日期差量改变起止，保留日内时刻和工期；端点按天调整对应日期、保留该端时刻、另一端不变。计算以公司日期为准，不能依赖设备时区。跨周移动按实际目标日期计算，拖住续接片段时按该片段的抓取日期求差量，不把任务开始日错误设为片段日；仅真实端点生成端点命中区。

日视图横轴/纵轴继续以一小时相对差量调整，保留原分钟；整条移动改变两端且工期不变，端点修改只改变一端。纵向全天区为原 allDay 和定时 fullDay 提供明确可触达的整条/端点操作区及键盘入口，仍仅在全天区展示、不复制到时间轴、不修改全天语义。操作只提交原任务完整排期，裁剪续接端不能冒充真实端点。

取消保留全部原始数据；逆序明确拒绝。月历键盘按天、日轴键盘按小时；完整起止预览、拖动后确认、Esc/pointercancel/lostcapture、触摸滚动及点击抑制沿用。拒绝继续使用月格宽度/24来计算月历拖动；小时精确安排留给日轴和详情。

### 2. 页面交互能力与任务命令权限分离

本人 Calendar task views 仍仅列当前有效负责人任务；只在该本人视图根节点启用框体/端点拖动，并重验已发布、未完成、非待审及 canReschedule。不能用全局 document 扫描把下属画布重新绑定为可拖动。表单不生成画布拖动入口；下属月/日/全天区不生成手柄、平移或独立调时按钮，但可进入普通任务详情。

普通详情不因从表单或下属进入被强制 readonly；各按钮继续按当前用户原有权限显示，服务端重验。现有仅排期 reschedule 允许正常可见的已发布未完成非待审任务，仅提交 SCHEDULE_FIELDS 和 reason，仍存为 change 审核，提交及生效时校验可见性/仅排期差异/版本。历史通知的专用只读例外不是正常可见权，不获得此入口。

当前业务责任方仍独占基础资料/负责人编辑，负责人进展/完成及其他专用命令各自鉴权。用户提出的“正常可见即可编辑基础字段”明确暂缓，留作后续决策，不变成本轮新权限任务；也不因本人画布当前恰好只有负责人任务而收紧现有 reschedule 接口。页面无拖动不等于详情所有操作被禁用。

### 3. 待审是日历展示投影，不是提前生效

已发布任务进入任意后续审核均使用虚线外框、淡底及审核提示，标签色保持；无排期变化仍在有效位置。包含新排期时，本人/下属日程只在提议位置显示，查询范围、框体、标题/日期时刻和当天清单都使用最小 pendingSchedule 展示副本。本人月历按日级几何，日轴按实际时段几何。

API 保留有效起止字段，pendingSchedule 仅含所需排期字段，不泄漏提议正文、标签或负责人；不覆盖 TASKS 等有效数据缓存。下属响应先校验当前人/会话再更新有效数据，展示副本不污染普通详情。任务表单、普通详情、提醒和统计继续使用有效版本。未发布创建申请不进入正常日程；重开待审可显示虚线，但完成及冻结边界仍禁止拖动。

松开仅预览/确认，成功提交才出现持久待审投影。创始人合法免审直接显示新有效实线；审核通过后新有效排期实线，驳回/撤回/失效恢复仍有效排期，刷新/重登/跨月/跨日保持唯一位置。待审期间冻结原有任务业务操作，评论仍独立鉴权。

### 4. 日志阅读与普通 HTTP 写入保持

日志正文共享 p-log-reading 的15px/1.55阅读变量，编辑/评论保留原用途；已归档日志页 self-only、卡片详情及日期/标签对齐继续回归。

P.mutation 优先使用原生 randomUUID，不可用时使用 getRandomValues 生成服务端接受的强随机 v4 标识；失败重试保留原 signature/ETag/幂等键，内容变化生成新键。保留普通 HTTP 真实提交、响应丢失重试只产生一笔记录的已有用例，不引入弱随机回退。

## Risks / Trade-offs

- [旧检查仍要求小时比例月条或下属可拖动] → 更新 check_schedule_drag_browser.js、check_subordinate_workspace_browser.js 的相应断言，用真实日级几何与入口矩阵验收；权限 API 检查仍保留，不通过恢复旧 UI 来满足旧用例。
- [日级绘图被误认为改变实际工期] → 检查原始起止、详情和提醒保持精确时刻，零时长不被改成全天，端点修改与整条平移分别验收。
- [全天区再次漏操作] → 纳入 verification V-001 的原 allDay 及 allDay=false/fullDay 两种真实样本，在本人纵向模式验证指针/键盘；下属同样样本验证无拖动。
- [待审投影污染有效数据或遗漏新月份] → 查询范围、详情缓存、原/新位置唯一性、每种审核终态及失权/换人迟到响应一起回归。
- [触摸误拖或起止命中相互遮挡] → 命中区与显示区分离，普通滑动/点击不提交，点任务两端分别命中。

## Migration Plan

无数据库迁移。按重新打开任务实施，保留旧报告与实施记录，更新本轮实施交接后再独立验证；不能以旧任务勾选或旧截图判 PASS。日志/HTTP既有实现不重做。先协调通知/创建 change 删除旧拖动定义，下属 change 对齐日级绘图与无拖动入口，再对共同版本验证；归档同步需以一致 delta 为准，主规格本轮不直接修改。云端发布另行处理。
