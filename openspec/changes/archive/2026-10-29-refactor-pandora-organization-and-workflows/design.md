## Goals / Non-Goals

**Goals:**

- 用一个可验证的位置模型提供四层身份、唯一直属关系及业务范围；组织变更、停用、接管、权限版本和待审刷新具有一致事务边界。
- 使独立管理员既能认证和留下管理来源，又不能进入员工组织或业务审核；员工业务 ID 与原创建来源稳定。
- 所有申请路径共享操作权校验、审核选择和生效逻辑，截止、有效版、幂等、通知边界保持一致。
- 新建与升级收敛于同一结构，演示准备可重复且只作用于显式目标；真实打包服务可验收移动与桌面交互。

**Non-Goals:**

- 不引入 ORM、前端框架、多管理链或可编辑角色引擎，不保留开发中旧员工 username 的兼容 API。
- 不重写 V1–V20 和旧归档记录；不把本次 proposal 当作迁移、演示清库或实现授权。
- 安卓、外部模型、系统推送、任务私人草稿等边界见 delta 的 Strict prototype scope；共用后端契约说明不等于安卓代码交付。

## Decisions

### 1. 用员工位置作为唯一组织事实

保留 `users.id` 为员工业务 ID；新增员工位置记录（示意名 `employee_placements`），一位有效员工恰好一个位置，种类为 founder / department_head / team_head / employee。公司固定记录 `founder_employee_id`，初始化或受控升级显式指定，普通管理 API 不允许更换。

| 位置 | 必要归属 | 直属上级来源 |
| --- | --- | --- |
| founder | 公司；无部门/团队 | 无，且必须等于公司固定创始人 |
| department_head | 一个部门；无团队 | 公司固定创始人 |
| team_head | 一个团队及该团队所属部门 | 该部门唯一 department_head |
| employee | 一个团队及其所属部门 | 该团队唯一 team_head |

`positions` 继续维护展示职位目录，员工职位外键必填，但不加入任何授权/审核分支。部门和团队保留独立实体，团队只有一个部门，不允许嵌套部门/团队制造额外管理层。负责人从唯一位置查询，不再双写另一个可编辑 lead 身份；旧 manager_id/rank/role 或负责人字段只在迁移阶段读取，切换后移除其作为独立事实的存储/写入接口。DTO 可输出推导后的 managerId、组织身份和展示字段，客户端不可反向编辑。

数据库通过员工位置主键、同公司复合外键、位置类型/归属 CHECK，以及负责人槽位的生成列唯一键确保“至多一位”；“单位必须有负责人”和“一位有效员工必须有位置”在公司锁内对完整最终状态验证。公司固定创始人引用和位置互相一致也在同一校验器中检查。不要求 MySQL 提供可延迟约束：在事务中删除受影响位置、写完整新位置，再检查最终覆盖，其他读事务看不到中间状态；外键始终保持有效。

不采用继续自由编辑 manager/rank 再补四层校验的方案，因为它仍容许多份相互矛盾的管理事实。也不把职位名直接映射为组织身份。

### 2. 管理员凭据独立，共同操作者使用明确身份

增加共同身份表（示意 `principals`）仅承载稳定主体 ID、公司、accountType 及账户状态；员工业务资料与员工凭据仍在 `users`，管理员凭据在 `admin_accounts`，每公司唯一。管理员账号名在当前无公司选择的管理员登录范围内唯一。升级尽量沿用原主体 ID，让原管理员审计可追溯；员工业务 ID 不改变。

会话与幂等记录关联共同主体，`Actor` 显式带 accountType；员工 Actor 的位置/上级来自位置模型，管理员不填员工位置。`AuthFilter`、`Writes`、密码/刷新/退出、事件审计不再假设所有主体都可在 users 查到。员工专用外键（有效负责人、原创建者、日志作者、当前业务审核人、业务接管人）仍指向 employees/users；审计操作者、管理记录、共同幂等主体等引用指向 principals。历史“作者/决定人”字段依真实用途区分追溯主体和当前业务资格，不能全量放宽成管理员可当审核人。

迁移逐项检查所有 `REFERENCES users` 与无外键的事件 JSON 操作者来源，包含 session、audit、idempotency、task_records、历史决定及管理通知；不得通过删除管理员历史或留下伪员工占位解决约束。若旧管理员真实占据员工业务关系，列为映射阻断并要求显式处理，不能自动冒充业务员工。

这比在 users 保留 admin 行并让所有候选永久排除更清楚，也避免独立管理员表与“仍要求员工用户名/部门/职位”半拆分。

### 3. 直接统一开发期认证和资料契约

继续使用 `POST /api/v1/auth/sessions`，定义严格二选一请求：

```json
{"accountType":"employee","phone":"13800000004","password":"..."}
```

```json
{"accountType":"admin","accountName":"admin","password":"..."}
```

accountType 必填，按类型只访问对应凭据命名空间；拒绝 username、缺类型、混合 phone/accountName 和不支持字段，返回 400 `INVALID_LOGIN_CONTRACT`，不尝试另一类型。账户错误保持 401，重复员工规范化登录键防御性返回 409 `LOGIN_KEY_AMBIGUOUS`；歧义请求不产生会话。数字管理员名与员工号码/密码相同也由明确类型隔离，不再运行旧客户端双身份猜测。上述替换显式废止旧可选 accountType/username 契约，但保留其“无跨类型回退、拒绝歧义”的目的。

员工姓名/手机号只允许管理 API 修改；本人资料请求只接受 avatar/email，密码继续独立命令。手机号建号必填、不可清空；规范化和全局有效员工唯一性保留，在数据库唯一约束和登录防御中共同保证。管理员改号更新登录键并撤销该员工全部会话，ID 不变；账号名/凭据修改也撤销管理员原会话。初始密码、首次强制改密、重置门禁和密码规则沿用当前业务。

清理不仅是 users.username：删除生成器、`organization_mapping_config.legacy_username` 及其索引/当前准备路径、字段解析/SQL、搜索 fallback、目录与会话 DTO、页面及当前测试依赖。演示身份用显式 seed key → 内部 ID/手机号清单解析，不用姓名或手机号作为公开用户名。历史迁移/文档保留；开发中的所有本轮 Web/脚本调用方一次更新。安卓只记录所需新契约，不为其保留兼容层。

### 4. 固定授权矩阵，移除旧授权运行依赖

`Access` 统一依据 accountType、当前位置、有效任务关系/正式接管关系裁决；`Actor` 不再从 `RoleCatalog` 加载任意角色、范围和等级。可返回由固定规则推导的 UI 行为标记，但不可编辑或作为客户端授权证明。移除角色授权控制器、菜单、写入口和无用途的旧表/依赖；旧 HTTP 写接口拒绝，不能保留暗门。

正常任务部门/团队归属仅看当前有效负责人，不看创建者部门。本人原始创建、有效负责和正式接管分别是对象关系；接管不改“我创建”过滤。部门/团队管理者的跨范围本人关系不应消失，普通员工不通过同团队扩权。日志与下属资料使用合法当前层级闭包；AI 统计/词云严格使用部门/团队矩阵，管理者建议仍限定本人任务，创始人公司建议。接管带来必要办理/访问权，不把其伪造成原始创建关系或扩大为整个组织范围。

公司隔离、有效版/待创建隔离、字段裁剪贯穿列表/搜索/统计/关联/候选/详情；手机号仅本人及当前管理链上级在授权详情读取，邮箱仅本人，管理员可录入号码但回执不回显，候选不含联系方式。

组织/接管使 `authz_version` 增长；旧 Actor、旧响应及幂等缓存必须在返回或重放前重验，保留 Writes 当前“版本检查先于幂等缓存”的顺序。多次查询组成的组织/任务 read model 使用同一一致性快照，或检测开始/结束权限版本变化后重读/拒绝，不能混合旧位置和新负责人。账号切换清掉前端缓存和迟到响应。

### 5. 组织计划按完整结果原子提交

管理端使用本地编辑草稿构造完整组织调整计划，提交一个版本化命令（建议 `POST /api/v1/admin/organization-plans`），包含预期组织/人员/单位版本、新旧人员最终位置、单位创建/删除、继任和所需停用/接管安排。预览只作提示，保存重新校验；不要求持久化草稿或新增通用审批系统。

沿用 Writes 的公司行锁、事务、If-Match 与幂等框架，顺序为：读取并检查版本 → 在内存构造最终组织/业务方案 → 检查四层、负责人覆盖、员工有效位置、职位、公司引用及业务完整性 → 写组织/业务变更 → 增加权限版本 → 刷新仍有效待审、写审计/outbox → 提交。任一步失败整笔回滚。创建单位可同时建负责人，单位无普通员工合法；不能先提交无负责人单位再补负责人。

读查询使用第4节的一致性策略。数据库 DDL 约束强化仍在业务事务之外，避免 MySQL 隐式提交；日常组织维护只用 DML。原有逐字段组织接口若保留，只能转换成同样的最终计划校验，不可绕过。员工团队接口删除写资格且接口直连也拒绝。

### 6. 审核选择与生效成为单一路径

将当前 `TaskService.creationRoute` 与非创建 `route` 整理为统一策略，结果携带 operation、businessOwner、reviewer、directApplyReason 或 blockedReason；预览、提交、详情、通知、刷新、实际决定都调用该策略。

| 操作 | 谁能发起 | 实际审核方 |
| --- | --- | --- |
| 创建/未发布创建重提 | 创建者本人 | 当前直属上级；固定创始人创建免审 |
| 基础字段/负责人修改、重开 | 当前业务责任方 | 当前业务责任方，因本人身份直接生效 |
| 进展/完成 | 当前有效负责人 | 当前业务责任方，相同则直接生效 |
| 专用交接 | 被交接人本人或其直属上级 | 当前业务责任方，相同则直接生效 |

先检查操作权、当前有效版、唯一待审/冻结、负责人/关联/排期及适用截止，再决定待审或直接生效。共同 apply 函数负责发布版本、执行状态/轮次、审计、事件和通知；直接生效可留“已直接生效”的申请/操作记录，但没有 pending，也不需要/允许再次批准。任何非创始人的缺失上级、不可用业务责任方都返回阻断，绝不沿负责人链上溯或兜底。

待审刷新先做截止/终态检查，再重算路线并重验原申请人当前操作资格。审核人变更留旧/新/原因/时间；若新审核人就是原申请人，重新校验完整提议后经同一 apply 路径直接生效。旧页面的决定不能调用另一套旧逻辑。申请人失去原操作资格时保持明确阻断，依业务处置办结或撤销，不能借改派使原非法提议自动发布；到期仍按现有失效规则结案。

保存有序负责人用于展示和差异，不再用于审核选择。专用交接候选按被交接人工作圈，普通负责人修改按全公司候选，两者分开。重开仍完整提交新排期，截止与提醒使用原有排期快照/轮次规则；显示全天分类不进入此路径。

### 7. 正式业务接管与负责人交接分开建模

新增任务当前业务责任记录/接管历史（示意 `task_business_owners` 和 append-only transfer records），未接管时有效责任方为 original_creator_id，接管后由唯一当前接管记录指定。保存对象、前后责任人、管理员 principal、发生时间、原因及版本；原任务 creator/time 永不覆盖。已完成任务仍有重开/审核责任，接管不能只扫描未完成任务。

停用计划需覆盖：有效未完成任务负责人、部门/团队岗位及下属、全部创建者业务责任（含已完成可重开任务）、待审，以及未发布申请。负责人专用交接先按第6节发起/审核，管理员指定接管人不意味着其可代业务申请/批准。需要他人审批的负责人交接先办结；正式停用命令检查引用的办结结果与版本，然后在同一最终事务提交岗位/接管/停用、刷新待审和通知、撤销会话。管理员始终只是管理来源。

停用前未发布创建申请可由原申请人正常撤销或办结；不能办结者在专用停用命令中由管理员撤销并明确记录该管理处置原因，这是仅针对未发布创建的受控例外，不开放代撤任意员工业务申请。历史 applicant 和 creator 不改写，不制造接管人的“原始创建”。非创建待审保留原申请人并按当前操作资格、责任方和截止刷新，必要时先由原申请人处理；无合法结果就拒绝停用。

用户在实施中确认：已完成任务的负责人若已停用，当前业务接管人可在重开时同步选择新的全公司有效业务员工负责人；重开提交仍须完整有效排期、非空有效负责人、当前业务责任方操作权及版本校验。未提供负责人时沿用现有负责人并重新校验，不自动把接管人变成负责人。此规则补齐“停用只要求交接未完成任务”后的重开路径。

接管后新业务通知/提醒把当前责任方用于原创建者责任收件槽；原创建者保留历史，不继续成为新审核人。接管人按接管关系取得正常任务访问，表单关系仍以原始创建/有效负责定义；可在详情单独展示当前责任方，无需新增“我创建”兼容假象。

### 8. 日程抽屉与当天清单使用独立覆盖状态

修改 `潘多拉-日程视图.js` 的最终 render/runAction、日历 CSS 及必要共享弹层，不依赖被它覆盖的基础函数。抽屉在日程容器内 absolute/fixed 覆盖、宽度以 42% 为起点，右侧保留日历；窄屏换行/纵滚，不用最小宽度撑全屏。遮罩、焦点循环、Esc/返回关闭、底层滚动锁和触发点恢复与现有弹层栈协作。

当天清单是月视图上独立 bottom sheet，不把 state.viewMode 改为 day。维护日期、月流/锚点/密度/滚动、清单滚动、返回焦点和嵌套详情状态；详情关闭返回清单，“查看日视图”才切 day。关闭仅出栈顶层，避免一次返回同时关闭详情/清单或重置今天。账号退出清除覆盖状态。

捕获月格统一激活事件，先检查滚动/双指/调高的抑制标记。跨日条用当前月周行七列几何、实际点击 x 和有效日期边界定位，考虑缩放/窄屏并夹取到实际覆盖列；键盘激活按当前聚焦日期，跨日条键盘可逐覆盖日选择，不固定首日。不以 task.start 代替命中日。

手势在顶部手柄或正文 scrollTop=0 且向下位移超过阈值后接管；普通滚动不夺取。pointercancel、触点增加或拖动不足恢复位置，按钮/遮罩/返回/Esc 独立可用。复用任务列表去重和排序，不再请求一份可能越权的日期任务集合。

### 9. 全天覆盖只改变当天投影

在 `dayCoverage` 附近增加统一投影分类：以公司业务日的本地午夜及次日午夜转换后的真实瞬时边界比较，区间采用 `[start,end)`，零时长为独立点语义。原始 allDay 或正时长且 start≤dayStart、end≥nextDayStart 的任务进入当天全天区；其余真实交集进入时间轴，两者按任务 ID 互斥。不用设备时区或固定毫秒数假定每个业务日长度。

复用全量全天滚动、标签色、置顶与时间轴并发布局；不改原 task.allDay/起止/工期/截止/提醒，详情继续显示原始排期。验证周二20:00—周四10:00、中间整天、午夜终止、午夜点任务、同日整天覆盖及超过五项重叠。

### 10. 精简页面，保留当前修复与必要查询

工作台仅删除日期区创建按钮及空占位；待办采用可收缩标题、不可挤压优先级列和滚动安全 padding/gutter，实际覆盖式滚动条需要浏览器检查。

任务表单移除指定 source/caption 文案、分类统计 DOM 和仅服务分类展示的计算；保留总项数/加载状态、完整结果筛选排序再分页、固定名称列和详情返回上下文。AI 页面统计继续存在，不因同名统计代码误删。本人/人员资料页面改只读姓名/手机号及四层身份，删除团队维护入口和用户名展示。

日志与个人事项已经修复，不列“修复 dateKey”伪任务：保留共享 toDateInput、日志真实 ID、人员日志入口清旧筛选、个人事项真实 ID，随新权限模型在真实服务回归。通知服务继续对评论存在/删除/当前对象权裁剪正文、对象/任务/审核跳转，历史任务入口也拒绝；撤回后的上级例外不放开受限评论，普通任务通知原历史只读例外不缩减。

## Risks / Trade-offs

- 管理员拆分牵涉共同外键及幂等主体 → 先扩展 principals 和引用、保留稳定 ID 后再移除 admin 员工行；对完整 schema 和历史事件逐项验收。
- 任意旧组织未必符合四层，无法纯 SQL 猜测 → 升级读取基于稳定 ID 的显式映射，缺创始人/负责人/职位/唯一手机号列为 blocker；受控管理修复可用，未就绪的正式业务关闭。
- MySQL DDL 隐式提交且不支持延迟约束 → 分阶段迁移、每阶段检查点；日常调整只用事务 DML 与唯一槽位索引，DDL 不夹入组织/接管事务。
- 刷新待审可能触发本人直接生效，与截止/扫描竞争 → 统一生效函数、公司锁、版本/终态检查；先失效检查再路由，真实并发验证不复活旧申请。
- 权限模型替换后缓存/聚合/通知可能保留旧数据 → 版本化 Actor、幂等和查询快照，撤权后检查列表、详情、聚合、旧通知和重放；评论例外独立回归。
- 半宽抽屉在320px内容拥挤，拖动可能误识别 → 文案换行/纵滚、清晰关闭入口、记录手势取消与滚动边界，在320/390/1440尺寸验证实际页面和焦点。
- 旧检查大量断言旧角色/自审/username → 按新契约改行为断言并保留仍适用的安全边界，不用删除失败断言充当适配。
- 公司级锁降低并发度 → 沿用当前本地服务设计，优先确保完整结果原子性；本轮不引入分布式事务/复杂分片锁。

## Migration Plan

1. 在隔离库备份当前 V20 结构和样例历史，生成稳定 ID 映射清单（创始人、单位负责人、位置、展示职位、管理员拆分、手机号冲突处理），报告阻断。记录旧迁移校验和；不读取/打印明文凭据。
2. 新增连续版本迁移，先扩展 principals/admin_accounts、固定 founder 依据、位置、业务责任及接管历史结构，放宽旧“所有用户必须有部门”的冲突约束；新建库也经过同一迁移链。脚本新旧结构过渡按实际阶段可识别，不在启动时清库。
3. 在维护/准备阶段以显式映射转换旧组织和管理员引用；对非演示库保持员工 ID、原始业务来源及历史。存在不能合法解释的数据则记录 blocker，管理员修复路径可用，不能跳过到最终开放。
4. 切换后端及所有本轮 Web/脚本到新身份、位置、权限与审核；对旧 pending 先做截止及有效资格检查，再按新路线刷新，合法本人审核自动生效并留原因，通知/outbox同步，不沿旧路线处理。
5. 用后续新迁移移除员工 username/索引/legacy_username映射、废弃角色授权依赖及可独立编辑的管理链/等级字段；完成新外键/唯一/CHECK与就绪门槛。最终 schema 不靠旧种子才合法，新建/升级结构比较一致。
6. 演示重建是显式独立命令：要求目标库名和演示标识校验，仅作用于目标库；稳定 seed key 清单映射新员工 ID/手机号，准备两次不重复，至少两部门各多团队、超过两页任务和全部规定场景。应用启动不执行任意清理。更新数据库说明、导出/快照和当前操作文档。
7. 构建 JAR、检查 Maven 静态资源白名单和内容 hash、以实际打包服务完成接口/浏览器/迁移/并发验证。证据保存在本 change 的实施记录及新 audit 目录，旧证据仅作回归参考；之后再进行独立 e13 verify。

回退：迁移不回写历史文件、不尝试在新结构上直接运行旧代码。MySQL DDL 不保证整链事务回滚；在停服/维护阶段从预迁移备份恢复隔离或明确目标库，再恢复配套旧服务/静态资源，撤销新会话；演示库可用受控重建恢复。已完成新增业务写入后应使用向前修复或完整备份恢复方案，不伪称可无损自动降级。
