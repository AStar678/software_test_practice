## Context

参见 `proposal.md` 的动机。当前 `潘多拉-交互原型.html` 是约 322 KB 的单文件：外层预览页通过 JSON 转义字符串向 iframe 注入约 288 KB 的内层应用，内层包含 6 组样式/脚本和本地存储状态。它已覆盖五个页面，但业务模型与入口明显超出 `需求初步整理.md`，继续在现有分支逻辑上删改容易留下隐藏入口和权限旁路。

本项目没有构建工具、后端或已有自动化测试；原型需要能够直接打开并在手机尺寸下使用。规格中的权限是交互演示规则，不构成真实客户端安全边界。

## Goals / Non-Goals

**Goals:**

- 保持一个可直接打开的 HTML 文件，降低演示与交付成本。
- 用集中、可检查的角色规则驱动五个页面、详情弹层和所有操作入口。
- 以少量静态示例数据覆盖每种核心状态，使审核、通知、父子任务和角色差异可以实际点击验证。
- 在 375、390、430 像素宽的手机视口中保持稳定布局，并兼顾桌面上的手机预览效果。
- 将原型代码规模与交互复杂度收敛到需求所需范围。

**Non-Goals:**

- 不实现真实登录、服务端权限、数据库、消息推送、AI 生成或跨设备持久化。
- 不设计管理员管理端；管理员仅作为需求边界说明。
- 不保留旧原型浏览器状态或兼容其数据结构。
- 不建立通用工作流引擎、通用审批中心或完整日历组件。

## Decisions

### 1. 重建单层单文件原型

将现有文件替换为同一文档中的预览工具栏、手机应用结构、样式和脚本，不再把整套应用编码成 JSON 后注入 iframe。桌面环境显示手机外框，窄屏环境直接铺满视口。

原因是单层结构更容易检查可见功能、调试响应式布局和验证无障碍属性，也能显著减少转义内容造成的维护负担。备选方案是在现有 iframe 内逐项删除功能，但旧状态和分支数量较多，难以证明越界能力已完全移除。

### 2. 身份切换属于预览层

预览工具栏提供上层、中层、下层三个固定示例身份，切换后调用统一渲染流程；应用内部“我的”页面不提供切换入口。管理员不放入身份选择器，因为本次没有管理员端可演示内容。

这样既能验证所有角色权限，又不会把演示手段误认为正式产品功能。备选方案是在“我的”中保留身份切换，但会违反最小个人页和严格范围要求。

### 3. 使用小型内存状态模型

脚本维护以下最小实体：

- `people`：姓名、角色、部门、直属上级。
- `tasks`：普通/抽象类型、父任务、创建者、负责人列表、起止时间、紧急程度、状态、进度和进度备注。
- `logs`：作者、时间、内容和可选任务关联。
- `notifications`：接收者、类型、任务和时间。
- `consultations`：中层、直属上层、内容与处理状态。
- `companyItems` 与 `personalItems`：导图的公司信息和个人摘录。

刷新页面恢复种子数据，页面内操作在当前会话中更新内存并立即重绘。不使用 `localStorage`，避免旧版状态污染新模型。备选方案是继续持久化，但这对演示价值有限并增加迁移与重置功能需求。

### 4. 权限通过集中派生函数实施

实现 `visibleTasks(actor)`、`visibleLogs(actor)`、`assignablePeople(actor)`、`canEditTask(actor, task)`、`completionReviewer(task)` 等单一规则入口。列表筛选、详情显示、表单选项和提交处理均复用这些结果，不能只隐藏按钮而保留可调用动作。

角色规则严格映射规格：上层为全公司范围；中层为本部门范围并只可派发给部门下层；下层仅为本人范围且不能派发。查看他人日志永远是只读。

### 5. 用明确状态展示两种审核

任务状态限定为 `pending-create`、`todo`、`doing`、`pending-complete`、`done`、`rejected`。中层/下层自建任务从 `pending-create` 开始；派发任务和上层自建任务从 `todo` 开始。普通任务提交完成后进入 `pending-complete`，由创建者或自建任务的直属上级审核；无更高审核人的上层自建任务直接进入 `done`。

不建立独立通用审批实体，审核所需的申请者、审核人和结果保存在任务状态及事件说明中。这样足以演示文档中的两种审核而不扩展成审批平台。

### 6. 抽象任务只汇总普通子任务

抽象任务使用 `type: abstract` 和子任务引用，不提供负责人进度输入或完成按钮。其完成数与百分比由普通子任务实时计算；至少展示一个“尝试涉足新产品”与“开辟北交校徽产线”的父子示例。

不支持任意深度任务树；本原型只展示一层父子关系，以控制界面与数据复杂度，同时满足需求示例。

### 7. 五页采用固定、任务导向的组件

- 导图保持 2×2 象限语义；手机上仍为两列紧凑布局，并允许页面纵向滚动。
- 视图使用月/周/日分段控件和轻量时间网格；碰撞任务在渲染前按“紧急优先、截止更近优先”排序，超额项合并为“+N”。
- 日志页承载写日志、创建/派发任务、自建任务审核和中层请示入口；其他页面只提供查看或与当前内容直接相关的任务动作。
- AI地图只渲染静态计算结果、CSS 词云和预置建议，不模拟真实 AI 请求。
- 我的只渲染姓名、部门和角色。

详情和表单使用同一种底部抽屉或对话框容器，避免为每个流程增加独立页面。通知用顶部铃铛打开最小列表，因为它是文档明确通知能力的必要可见载体。

### 8. 样式与图标保持轻量

沿用清爽、低干扰的工作工具风格，使用现有可复用的内联图标路径或简单文字符号，不新增网络资源和依赖。本人负责与本人派发任务使用颜色之外的标签/线型双重区分，紧急程度与审核状态使用文字徽标，避免仅依赖颜色表达。

## Risks / Trade-offs

- [单层重建可能遗漏旧原型中仍有价值的细节] → 以规格而非旧功能为验收清单，只有规格覆盖的行为才迁移。
- [客户端过滤可能被误解为真实权限安全] → 在预览层标明这是交互原型，并避免宣称具备生产安全能力。
- [手机 2×2 象限信息密度较高] → 每个象限限制条数和行高，提供内部“查看更多”或滚动时只用于展示本象限剩余的同类内容。
- [类甘特视图难以在窄屏完整表达] → 月视图按天、周/日按时刻保证语义准确，允许时间轴横向滚动而不缩小文字。
- [静态示例日期随时间失效] → 由页面加载日计算相对日期与时刻，使临期、今天和昨天场景始终可见。
- [删除本地存储会使刷新后操作丢失] → 接受该原型取舍；所有关键状态在种子数据中均有示例，不增加重置功能。

## Migration Plan

1. 在保持文件名不变的前提下重建 `潘多拉-交互原型.html`，先建立预览层、五页壳和集中状态模型。
2. 逐页迁移规格内功能，随后接入任务、日志、审核、通知和请示交互。
3. 删除旧 iframe 文档、本地存储键和所有未列入规格的入口与处理分支。
4. 直接打开 HTML，分别以三个示例身份执行规格场景；在 375×812、390×844、430×932 以及桌面视口检查布局、遮挡和溢出。
5. 如需回退，通过版本控制恢复单个 HTML 文件；本次没有服务端数据迁移。
