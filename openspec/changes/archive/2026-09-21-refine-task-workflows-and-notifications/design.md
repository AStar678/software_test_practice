## Context

参见 `proposal.md` 的动机和 delta spec 的行为约束。当前原型是可从 `file://` 直接打开的 HTML、CSS、经典 JavaScript 三文件应用，所有数据都来自会话内种子数组，没有后端或构建步骤。现有任务同时包含 `type`、`start`、`due`、`progress`、`progressNote` 和工作流 `status`；新建任务却把 `start` 固定为创建瞬间，导致视图中的时间跨度并非用户排期。周视图又在整个任务主体下铺设透明下钻按钮，任务/上级/负责人选择则直接渲染长列表或原生下拉框。

通知目前只面向任务并用 `create`、`due`、`emergency` 三种类型，其中“临时紧急”既是通知类别又被机械写进任务标题。现有通知数组和少量创建通知函数只是原型演示，不构成完整触发机制。

## Goals / Non-Goals

**Goals:**

- 让任务的创建时刻、计划起止范围和全天语义彼此独立，并让三个日历视图消费同一套时间范围派生逻辑。
- 以可回滚的二级选择界面处理大量任务和人员候选，保持权限过滤、搜索、确认与取消行为一致。
- 将任务完成表达收敛到离散状态和文字进展备注，删除所有百分比进度分支。
- 让通知样例准确覆盖任务变更、审核和请示语义，同时明确它仍是静态交互原型。

**Non-Goals:**

- 不实现通知事件总线、定时临期扫描、服务端推送、持久化或跨会话数据迁移。
- 不引入组织树管理、拼音/模糊分词搜索、远程分页或通用全局搜索。
- 不建立通用任务类型系统、任意工作流配置或由子任务自动控制父任务状态的规则。

## Decisions

### 1. 使用一个可执行任务模型，父子关系只表达拆解

删除 `type: "abstract"`、`progress`、`effectiveProgress` 和抽象任务派生状态。每个任务都必须有负责人并可按同一工作流执行；`parentId` 继续表达拆解关系，详情可显示子任务逐项状态和“已完成数/可见子任务数”，但父任务状态只能由其自身操作改变。

保留现有的 `progressNote` 存储字段以降低无关迁移面，但界面统一称为“进展备注”，不再与数值进度绑定。原抽象示例不保留特殊类型：将其改写为有明确交付物、负责人和自身状态的可执行父任务，或在没有独立执行价值时删除并重新挂接子任务。所有带“自建任务：”或“临时紧急：”等系统式前缀的标题一并改为真实业务标题，属性通过徽标表达。

备选方案是把抽象任务改名为“项目”或“目标”。这仍会引入第二套对象生命周期、负责人规则和日历语义，而当前需求只需要任务拆解，因此不保留。

### 2. 显式记录创建时间，并用统一范围助手解释全天任务

任务增加 `createdAt` 和 `allDay`。`createdAt` 在种子数据中显式给出，新建时记录当前时间，编辑永不覆盖。`start` 与 `due` 继续使用本地 `Date`，非全天任务保存用户输入的精确时刻；全天任务把两个值规范化到对应日期的本地零点，显示时只格式化日期。

所有交集、跨度和条形定位通过一个 `taskRange(task)` 助手读取。对非全天任务返回 `[start, due]` 的实际时间范围；对全天任务返回从开始日零点到“截止日次日零点”的左闭右开区间。这样截止日期自然完整包含在任务中，不需要写入 `23:59:59.999`，也不会在跨日和夏令时边界靠毫秒补丁维持正确性。表单验证按相同语义拒绝倒置范围。

创建/编辑表单将“全天”作为二元开关。关闭时显示开始日期、开始时刻、截止日期、截止时刻四个输入；开启时仅显示两个日期输入。切换到全天时保留日期并忽略草稿时刻，切回时恢复合理的默认时刻；最终只有当前模式的输入参与保存。

备选方案是给全天任务另设 `startDate`/`endDate` 字符串。它能避免时间对象，但会迫使排序、交集、详情和现有渲染器长期处理两套字段，原型收益不足。

### 3. 用可复用任务选择器服务日志关联和上级任务

日志关联任务与上级任务都从表单进入同一种二级选择界面，界面包含当前选择、可清空操作、`type="search"` 输入、实时结果列表和明确空状态。搜索值经过 `trim` 和大小写归一化后对任务名称做包含匹配；空查询显示完整候选集。

两种上下文只共享呈现和搜索，不共享候选规则：日志关联候选为作者当前可见的全部任务；上级候选为当前身份可见任务，再排除当前任务及其所有后代，避免任意深度循环。选择结果只有点击“确认”才写回表单草稿，“取消/返回”恢复进入选择器前的值。

备选方案是在原生 `select` 上方增加过滤输入。移动端原生下拉无法稳定展示动态过滤后的上下文与空状态，也难以在超长标题中确认当前选择，因此采用独立界面。

### 4. 负责人选择采用“部门范围 + 姓名搜索 + 持久多选”

任务表单只显示已选负责人摘要和“选择负责人”命令。二级界面先展示当前身份可用的部门控件，选定部门后才显示姓名搜索与人员列表；每个人员项包含姓名、角色和部门，并使用复选框表达多选。搜索只过滤当前部门，切换部门不清空工作副本，顶部持续显示跨部门已选人数和可移除的已选摘要。点击“确认”后整体替换表单草稿中的负责人，取消则丢弃工作副本。

部门和人员都从 `assignablePeople(actor)` 派生，不能先读取全员再只在 DOM 中隐藏。上层可切换其可派发人员所在的全部部门；中层只看到预选且不可越权切换的本部门；下层负责人固定为本人，不打开冗余选择界面。提交保存时再次校验至少一名负责人及全部 ID 的权限，避免仅靠界面约束。

备选方案是把人员搜索放在任务表单内。它仍会让时间、紧急程度、父任务和人员结果竞争一个狭窄抽屉的空间，也无法清楚表达跨部门多选，因此单独成页。

### 5. 表单使用显式草稿承接二级界面往返

现有表单状态主要留在 DOM 中，打开另一个 sheet 后无法可靠恢复。为任务编辑和日志编辑分别建立短生命周期草稿对象：打开表单时从实体复制，输入变更和进入二级界面前同步到草稿，选择器确认只修改草稿，最终保存才写入 `TASKS` 或 `LOGS`。关闭最外层表单时丢弃草稿。

sheet 导航继续复用现有返回结构，但返回时重新按草稿渲染表单。选择器内部另建工作副本，从而同时满足“选择器取消”和“整个表单取消”两层回滚语义。切换演示身份时清空所有编辑草稿，避免把上一身份的候选 ID 带入新权限范围。

备选方案是进入选择器前从 DOM 临时序列化、返回后再逐项回填。这会把业务状态绑定到 HTML ID，且全天模式与跨部门多选很容易漏字段。

### 6. 周视图只让标题按钮承担下钻，全天任务在日视图分层展示

周视图把七个不可操作的轴标题 `span` 改为等宽 `button`，每个按钮携带对应日期的 `data-drill-day` 和完整无障碍名称。删除主体中的 `.g-drill` 透明覆盖层，使任务区空白没有点击行为，任务条仍由现有事件委托打开详情。

月、周视图都使用 `taskRange` 定位：全天任务贴合完整日期列，非全天任务保留时刻精度。日视图在小时轴上方增加稳定高度的“全天”带，只列出覆盖该日的全天任务；小时泳道只接受非全天任务。全天带沿用任务颜色、关系标记、溢出入口和详情操作，不把全天任务伪装为 00:00 到 24:00 的普通时段。

备选方案是保留透明主体按钮并在标题上增加第二入口。两个热区会继续造成误触，也与月视图已经采用的明确标题入口不一致。

### 7. 状态和进展备注取代数值进度

保留 `pending-create`、`todo`、`doing`、`pending-complete`、`done`、`rejected` 六种现有状态及其审核流。负责人操作改名为“更新进展”，表单只含文字备注；从 `todo` 首次保存备注时转为 `doing`。提交完成、批准、退回继续分别驱动 `pending-complete`、`done` 和 `doing`，上层自建且无审核人的任务直接完成。

删除创建表单初始进度、详情进度条、列表百分比、审核百分比、子任务百分比、数值校验和所有以百分比推导状态的代码。状态徽标是唯一完成情况表达，文字备注是补充说明而非另一套状态。

备选方案是在更新进展时提供任意状态下拉。这样会允许跳过审核状态或进入不符合身份的状态，削弱现有审核规则，因此仍由明确动作推进状态。

### 8. 通知使用通用目标的代表性种子记录

把通知记录从强制 `taskId` 改为 `targetType`、`targetId`、`type`、`recipients`、`time`、`read` 和简短说明。类型至少覆盖任务创建、任务信息修改、紧急程度修改、状态变化、临期提醒、审核请求/结果、请示/回复。打开通知时按目标类型进入任务详情、审核筛选或请示内容，并在跳转前复用对应可见性检查。

通知继续全部由种子数据提供；删除或停用当前只覆盖创建场景的局部触发函数，避免“有些操作会通知、有些不会”的原型行为被误解为完整规则。任务变更样例的接收者集合显式包含创建者、当前负责人以及该次被移除的负责人；审核和请示样例各自指向处理人或结果接收人。

原 `emergency` 类型改为 `urgency-change`，示例任务标题去掉“临时紧急”前缀并保留 `urgency: "紧急"`。临期提醒继续存在，因为它是时间事件而不是任务变更，两者在通知列表中使用不同标签。

备选方案是补齐所有表单动作的内存通知生成。那会开始实现用户明确排除的触发机制，还需要定义去重、通知自己、批量修改和时间扫描等额外规则，因此本次只纠正语义和样例。

### 9. 同步修正需求来源并做残留扫描

`需求初步整理.md` 中删除抽象任务的肯定性描述，将任务属性改为创建时间、起止排期、全天、状态和进展备注，并把通知描述改为“任务及审核/请示的相关变动通知相关人员”。文档同时注明原型不实现触发机制。

实现完成后对 `abstract`、`抽象任务`、`progress`、百分号进度文案、`progress-track`、`临时紧急` 和主体 `data-drill-day` 做全仓扫描。只有历史 OpenSpec 归档可以保留旧术语；当前原型、需求文档和新规格不得残留旧行为。

## Risks / Trade-offs

- [全天任务采用本地日期，直接使用毫秒差可能在夏令时边界出现偏移] → 所有日期推进使用日历日期助手和左闭右开范围，不用固定 24 小时毫秒数推算天数。
- [二级选择器往返可能丢失尚未保存的表单输入] → 表单先写入显式草稿，再打开选择器；覆盖创建、编辑、确认、取消和身份切换路径。
- [跨部门多选会让“当前部门搜索结果”与“全部已选人员”看起来不一致] → 固定显示总已选摘要，部门只限定候选列表，并允许从摘要直接移除。
- [删除百分比后 `todo` 与 `doing` 缺少自动量化依据] → 用首次保存进展备注作为明确的开始信号，其他状态继续由审核动作驱动。
- [通用通知目标增加样例分支] → 限定为任务、审核和请示三类目标，统一做目标存在性、收件人和可见性校验；不扩展为通用消息中心。
- [旧种子数据的抽象任务没有负责人和创建时间] → 在同一数据迁移步骤中改写为可执行任务或删除，并为所有种子任务补齐负责人、创建时间和全天标志后再移除兼容分支。

## Migration Plan

1. 先更新任务种子模型和时间/状态派生助手，为所有现有任务补齐 `createdAt`、`allDay` 与有效负责人；改写或删除原抽象任务和“临时紧急”标题样例。
2. 引入任务与日志表单草稿，再实现任务搜索选择器和按部门的负责人选择器；保存处理统一从草稿读取并执行权限、循环和时间范围校验。
3. 切换三个日历渲染器到统一 `taskRange`，将周标题改为下钻按钮，删除主体命中层，并增加日视图全天带。
4. 删除所有数值进度输入、计算、渲染和样式，保留离散状态、文字进展与现有创建/完成审核流。
5. 泛化通知种子与详情跳转，补齐变更、审核、请示样例并移除局部触发逻辑；同步更新 `需求初步整理.md`。
6. 运行 JavaScript 语法检查、术语残留扫描，并从本地文件在桌面和窄屏下按三个身份验证搜索、选择器回滚、定时/全天任务、日历下钻、状态审核和通知跳转。

回滚通过版本控制同时恢复 JavaScript、CSS 和需求文档。原型没有持久化数据或服务端 schema，不需要数据回滚脚本。
