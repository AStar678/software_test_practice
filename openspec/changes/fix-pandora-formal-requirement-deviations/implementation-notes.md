  (1 request past its deadline). The phase-2 administration flow can now supply that mapping, but it has
  not been applied to the snapshot; the columns stay **nullable** on that database until it is, and
  `expirePending` still belongs to section 5. Verify both the staged state and the tightened state (a

- `tasks.due_version` is deliberately retained but no longer updated; `schedule_version` is the live
  identity from phase 6 onward. Confirm no new code path increments `due_version`.
- `task_versions.applied_at` is only backfilled for versions that are currently effective (33 of 60
  `applied` rows); historical versions intentionally keep NULL rather than an invented time.
  `task_assignments` therefore shows 27 `legacy-estimate` rows — legitimate, not a defect.
- `approval_requests.route_basis_assignee_id` / `route_reason` / `route_authz_version` are populated
  only by the phase-4 routing code; the V6 backfill writes `request_reassignments` with
  `source='migration'` and the old reviewer on both sides so the recomputation is auditable.
- `notifications.expires_at` was backfilled with `DATE_ADD(occurred_at, INTERVAL 3 MONTH)` on the
  stored UTC instant. That is exact for `Asia/Shanghai` (no DST); phase 7 must compute the same rule
  from the organization zone for DST zones. `notifications.row_version` and `read_at`/`hidden_at`
  still drive the ETag; the open-on-read command is not implemented yet.
- `user_task_pins` and `task_assignments` have no writer yet (phases 9.1/9.4); they are schema-only so far.
- `work_log_conflict_archive` holds the 4 merged duplicate bodies. Any later verification of "全部原文保留"
  must read both `work_logs` and this archive table.
- The precheck script interpolates organization/author/date values read from the database into follow-up
  SELECTs; they are UUIDs, ISO dates and integers, but it is not parameterised SQL and should be reviewed
  before it is pointed at a non-local database.
- `Db.camel` only upper-cases the character following `_`, so MySQL's uppercase `information_schema`
  labels (for example `IS_NULLABLE`) do not map as expected. `OrganizationConstraints.isNullable` works
  around this with an explicit alias. This trap will reappear for any new `information_schema` query.
- The `pandora` migration-rehearsal snapshot copy still exercises only the staged path. The
  administration flow that supplies the mapping (2.1) exists, but **nobody has run it against the
  snapshot**, so the 3 open blockers on that database are unchanged. A verifier wanting to see the
  tightened end state on legacy data must first apply department/position mappings to all 7 accounts
  and 3 teams, then confirm `OrganizationConstraints.tryTighten()` flips the columns to `NOT NULL`.
- `OrganizationService` rejects a team whose `department_id` differs from the employee's department
  and requires an explicit organization `level` (0-100). Both are deliberate readings of the
  "Organization and administration" requirement; confirm they are the intended ones.
- `Writes.runOutcome` is the only path that returns a one-time secret; the idempotency cache stores
  only the replayable part. The lifecycle suite searches the stored `idempotency_keys`, `audit_logs`
  and `domain_events` payloads for the generated secret and the chosen new password. Verify that no
  later command routes a secret through `Writes.run`.
- The account flows **were** driven in headless Chrome (login, first change, everyday change, reset).
  The **administration console's own click-through was not**; `admin.html` is verified as served by
  the packaged application plus the HTTP operations it performs. Do not treat the console as
  browser-verified end to end (that is task 11.4).
- The forced-change gate is keyed on `users.must_change_password` at request time. A restricted
  session therefore cannot become unrestricted by refreshing; conversely, an administrator reset
  invalidates any browser session, which the browser suite asserts by reloading the page.
- `POST /api/v1/auth/password` is deliberately **not** routed through `Writes`, so it carries no
  `Idempotency-Key` and is not replay-protected. A duplicated submission fails on the second attempt
  because the current password no longer matches — confirm that is acceptable.
- `AuthService.changePassword` serializes on the user row but not on the organization lock. Two
  simultaneous changes for the same account cannot both win, but the loser sees the plain
  `INVALID_CURRENT_PASSWORD` message rather than a retry hint.
- The seeded demo accounts keep `must_change_password = FALSE`, so they sign in directly; only
  administrator-created or administrator-reset accounts hit the gate. Confirm that is the intended
  demo experience.
- Sections 4-11 are out of this goal's scope by explicit user instruction. Everything those sections
  own (ordered reviewer routing, expiration, reminders, notification lifecycle, log rules, calendar,
  analytics, integration verification) is unimplemented and must not be reported as verified.
